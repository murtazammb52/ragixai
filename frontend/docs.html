RAGixAI — Technical Documentation

A deep-dive into every design decision: what each component is, why it was chosen over alternatives, and how each piece fits the overall system.

System Overview

RAGixAI is a local-first Retrieval-Augmented Generation system over SEC EDGAR financial filings. It takes natural-language questions about public company financials and returns cited answers grounded exclusively in the retrieved filing text — not the model's training data. The system runs entirely on consumer hardware with no cloud API dependencies.

Scope and limitations: This is a research and reference implementation of RAG architecture running on a Windows laptop with an NVIDIA MX450 GPU (2 GB VRAM) and llama3.2 (3B parameters) via Ollama — a small, weak model compared to GPT-4 or Claude. Generation takes 143–215 s per query at ~25 tok/s. The 3B model has known weaknesses on financial reasoning: it paraphrases exact figures, struggles with multi-hop questions, and cannot perform arithmetic. Every configuration reflects these hardware and model constraints. This system is suitable for demonstrating RAG architecture and offline evaluation — not for interactive production analyst use.

Why RAG, not fine-tuning?

Design Rationale

Knowledge currency: SEC filings are published quarterly. A fine-tuned model's knowledge cutoff is its training date — adding the latest 10-Q requires re-running GPU training (days, A100-class hardware, thousands of dollars). RAG's knowledge store is a ChromaDB collection: adding a new filing takes 5 minutes of ingest + embed. The model never changes; only the corpus does.

Hallucination control: A fine-tuned model "knows" financial data from training and can generate plausible-sounding but wrong numbers with high confidence — it interpolates from the training distribution. RAG physically cannot generate a fact that isn't in a retrieved chunk, and every claim is anchored to a cited source that can be audited. For financial data (where an incorrect revenue figure has legal and investment consequences), this is essential.

No GPU training required: Fine-tuning even a small 7B model requires multi-day runs on A100s. RAG requires only inference — the smaller task that fits on consumer hardware.

Why local-first?

Design Rationale

Data privacy: Financial analysts often annotate queries with internal context ("what are the risk factors for AAPL relative to our portfolio position?"). Sending this to a cloud API violates data governance policies in many financial institutions. Running entirely on-device means no data leaves the machine.

Cost: The evaluation harness runs 7 configs × 20 QA pairs = 140 calls in a single test run. At GPT-4 pricing (~$0.03/call), that is $4.20 per run. With unlimited local Ollama calls, each run costs $0. At development velocity (dozens of evaluation runs), this compounds significantly.

Latency: Cloud API round-trips add 500ms–2s of network latency. Local inference via Ollama on the MX450 adds ~155–185s of compute latency per query — LLM generation at ~25 tok/s dominates end-to-end time. For offline evaluation this is acceptable; interactive use targets lower num_predict to reduce generation length.

Stage 1 — Data Ingestion

backend/pipeline/ingest.pyscripts/run_ingest.pydata/raw/edgar/data/raw/edgar/manifest.json

The ingestion layer downloads SEC regulatory filings directly from the official SEC EDGAR REST API, strips HTML, normalizes whitespace, and writes structured plain-text documents to disk. This is the first and only stage with a network dependency — all downstream stages work from local files.

What is SEC EDGAR?

EDGAR (Electronic Data Gathering, Analysis, and Retrieval) is the SEC's mandatory public filing database. Every US-listed public company must submit quarterly and annual reports here within defined deadlines. The REST API at data.sec.gov provides programmatic access to filing metadata and full document text with no authentication, no API key, and no rate limit beyond 10 requests/second. The SEC requires only a descriptive User-Agent header identifying the application and a contact email.

Why the EDGAR API directly?

Design Rationale

Freshness: Financial datasets on HuggingFace (EDGAR-CORPUS, FinancialPhraseBank, SEC-BERT corpora) are static snapshots frozen at a release date — they do not include filings after that date. Going directly to EDGAR allows ingesting a 10-Q the day it is filed. For an evaluation system that needs to match FinanceBench's 2020–2023 range exactly, controlling the exact filing scope is essential.

Completeness: Pre-packaged datasets often extract only specific sections (Item 1, Item 7) or truncate large filings. The EDGAR API provides the full primary document — all sections, all footnotes, all tables — which is necessary for retrieval coverage of obscure financial line items.

No licensing restrictions: EDGAR data is public domain under US government copyright exemption. HuggingFace datasets may carry additional license terms depending on how they were processed. Direct EDGAR access has no such ambiguity.

CIK Number Registry and API Authentication

Every EDGAR filer has a unique Central Index Key (CIK) — a 1-to-10-digit number assigned at registration that never changes. The ingester hardcodes CIKs for all 10 tracked companies because they are stable identifiers that make the CIK lookup offline and instantaneous. For API calls, the CIK is zero-padded to 10 digits. The only authentication mechanism is a descriptive User-Agent header identifying the application:

TICKER_TO_CIK = { "AAPL": "320193", "MSFT": "789019", "AMZN": "1018724", "GOOGL": "1652044", "META": "1326801", "NVDA": "1045810", "TSLA": "1318605", "JPM": "19617", "BAC": "70858", "WMT": "104169", } EDGAR_HEADERS = { "User-Agent": "RAGixAI capstone murtazammb@gmail.com", "Accept-Encoding": "gzip, deflate", }

The User-Agent is required by SEC policy — requests without it are blocked. The contact email allows the SEC to reach out if automated access patterns cause issues. This is the only "authentication" the API uses.

Download Flow — Step by Step

For each (ticker, target_years, max_filings) combination, the ingester executes a 6-step sequence:

# Step 1: Fetch filing index for the company url = f"https://data.sec.gov/submissions/CIK{cik.zfill(10)}.json" data = httpx.get(url, headers=EDGAR_HEADERS).json() # Returns: {"name": "Apple Inc.", "filings": {"recent": { # "form": ["10-K","10-Q","10-Q",...], # "accessionNumber": ["0000320193-23-000077",...], # "filingDate": ["2023-11-03",...], # "primaryDocument": ["aapl-20230930.htm",...] # }}} # Step 2: Filter to target form types and years (max_filings limits per-form count) filtered = [(acc, date, doc) for form, acc, date, doc in zip(forms, accs, dates, docs) if form == "10-K" and date[:4] in target_years][:max_filings] # Step 3: Build the filing document URL from accession number acc_clean = acc_number.replace("-", "") # "0000320193-23-000077" → "000032019323000077" doc_url = f"https://www.sec.gov/Archives/edgar/data/{cik}/{acc_clean}/{primary_doc}" # Step 4: Skip if already downloaded (idempotent) out_path = raw_dir / f"{ticker}_{year}_{form_type}.txt" if out_path.exists(): logger.info(f"Skipping {out_path.name} — already downloaded") continue # Step 5: Fetch, strip HTML, normalize whitespace html = httpx.get(doc_url, headers=EDGAR_HEADERS).text soup = BeautifulSoup(html, "lxml") text = soup.get_text(separator="\n") text = re.sub(r"\n{3,}", "\n\n", text) # collapse excess blank lines out_path.write_text(text, encoding="utf-8") # Step 6: Append metadata to manifest.json manifest.append({"doc_id": f"{ticker}_{year}_{form}", "ticker": ticker, "company_name": company_name, "year": year, "form_type": form, "path": str(out_path)})

Idempotency — Safe to Re-run

Before fetching any document, the ingester checks if the output file already exists at data/raw/edgar/{TICKER}_{year}_{form}.txt. If it does, the download is skipped entirely — no HTTP request is made. This makes ingestion safe to re-run after a partial failure or network timeout: previously downloaded files are preserved and only missing files are fetched. Running /ingest-docs twice has the same result as running it once.

The --max-filings Subtlety

Critical parameter: The SEC EDGAR submissions endpoint returns the N most recently filed documents of any type, sorted by date descending, before any year filtering is applied. With --max-filings 3 and --years 2020: the API returns the 3 most recent 10-K filings (2024, 2023, 2022), then the year filter discards all three because none match 2020. Result: 0 files downloaded, no error message. The fix is --max-filings 10 — fetch enough filings that the year filter can find matches for historical years.

Manifest Structure

The manifest.json file is the handoff artifact between ingestion and chunking. It is a JSON array where each entry describes one downloaded filing. The chunker reads this file to find which files to process and what metadata to attach to each chunk.

[ { "doc_id": "AAPL_2023_10-K", "ticker": "AAPL", "company_name": "Apple Inc.", "year": 2023, "form_type": "10-K", "path": "data/raw/edgar/AAPL_2023_10-K.txt" }, ... ]

Rate Limiting

A time.sleep(0.15) delay runs between every HTTP request, limiting throughput to ~6 req/s — well below the 10 req/s SEC limit. Exceeding the limit causes a 429 "Too Many Requests" response and a 15-minute block. The sleep also reduces memory pressure during batch downloads by preventing simultaneous large HTML file parsing.

Stage 2 — Document Chunking

backend/pipeline/chunker.pyscripts/run_chunk.pydata/processed/chunks/chunks_recursive.jsonl

A 10-K filing is 80–200 pages of dense text — roughly 40,000–100,000 tokens. This is far larger than any embedding model's input window (256 tokens for all-MiniLM-L6-v2) or any LLM's context budget (the generator uses 5 chunks × ~500 tokens = ~2,500 tokens for context). Chunking splits each document into overlapping segments that are individually embeddable and retrievable while retaining enough surrounding text to answer a question without needing adjacent chunks.

Why overlapping chunks?

Design Rationale

Financial facts are sentence-spanning: "Net income for fiscal year 2023 was $96.9 billion, compared to $99.8 billion in fiscal year 2022, a decrease of 3%." This sentence must appear complete in at least one chunk for the retriever to find it. Without overlap, a chunk boundary might split this sentence — the figure $96.9 billion appears in one chunk, the comparison to $99.8 billion in the next, and a query about "year-over-year net income change" retrieves neither completely. With 50-token overlap, any sentence within 50 tokens of a chunk boundary appears in full in the adjacent chunk as well, ensuring complete sentence coverage.

Three Chunking Strategies

Strategy 1: Recursive Character (Default)

What it is: LangChain's RecursiveCharacterTextSplitter tries each separator in priority order. If a paragraph boundary (\n\n) produces a chunk of acceptable size, it uses that. If the resulting piece is still too large, it recurses with the next separator (\n, then ". ", then " ", then character-level as a last resort). It never splits mid-sentence unless there is genuinely no other option within the character budget.

class RecursiveCharChunker: def __init__(self, chunk_size=512, overlap=50): self.splitter = RecursiveCharacterTextSplitter( chunk_size=chunk_size * 4, # 512 tokens × 4 chars/token ≈ 2048 chars chunk_overlap=overlap * 4, # 50 tokens × 4 chars/token ≈ 200 chars separators=["\n\n", "\n", ". ", " ", ""], ) def chunk(self, text, metadata): parts = self.splitter.split_text(text) return [ {"text": p, "metadata": {**metadata, "chunk_index": i, "strategy": "recursive"}} for i, p in enumerate(parts) if len(p.strip()) > 50 # filter trivially short fragments ]

Strategy 2: Fixed-Size

What it is: Uses tiktoken (OpenAI's tokenizer, cl100k_base encoding) to split at exact token boundaries. Always produces chunks of exactly the specified size in tokens — no size variance, no sentence awareness. Useful for comparison experiments because chunk size is perfectly controlled.

class FixedSizeChunker: def chunk(self, text, metadata): tokens = self.enc.encode(text) # tiktoken, cl100k_base for start in range(0, len(tokens), self.chunk_size - self.overlap): chunk_tokens = tokens[start:start + self.chunk_size] chunk_text = self.enc.decode(chunk_tokens) # may split mid-word

Strategy 3: Semantic

What it is: Embeds each sentence with all-MiniLM-L6-v2 and inserts a chunk boundary wherever the cosine similarity between adjacent sentence embeddings drops below 0.5. Produces topically coherent chunks — each chunk covers one "topic" without straddling a topic shift. Requires a forward pass per sentence, making build time ~10× longer than recursive.

class SemanticChunker: threshold = 0.5 # cosine similarity drop → new chunk min_sentences = 3 # chunks must have ≥ 3 sentences before splitting def chunk(self, text, metadata): sentences = re.split(r"(?<=[.!?])\s+", text) embeddings = model.encode(sentences, batch_size=32) for i in range(1, len(sentences)): sim = np.dot(embeddings[i-1], embeddings[i]) # cosine (normalized) if sim < self.threshold and len(current) >= 3: # insert boundary here
Why Recursive is the default

vs. Fixed-Size: Fixed splitting bisects financial sentences mid-clause because it has no concept of sentence structure. "Net income increased 23% to $29.7 billion, driven by strong iPhone sales [SPLIT] in Greater China" — the crucial qualifier "in Greater China" appears isolated in the next chunk and doesn't help answer "what drove net income growth." Recursive splitting keeps the sentence intact unless the overall chunk would exceed the character budget.

vs. Semantic: Semantic chunking is semantically superior but practically problematic: variable-length chunks (some 200 tokens, some 900 tokens) make it hard to predict retrieval coverage; build time is ~10× longer; and the quality improvement over recursive is modest for well-structured financial filings that already have consistent paragraph boundaries. Recursive gives consistent chunk sizes and paragraph-level coherence for one-time build cost.

Why 512 tokens / 50-token overlap?

Parameter Rationale

Chunk size — 512 tokens (≈ 2,048 characters): all-MiniLM-L6-v2 has a 256-token maximum input. Inputs longer than 256 tokens are truncated — the model sees only the first 256 tokens of a chunk and ignores the rest. Using the 4 chars/token heuristic (1 char ≈ 0.25 tokens for English text), a 2,048-char chunk is ~512 tokens before tokenization, typically yielding ~400–480 actual tokens — within the embedding model's window.

A 512-token chunk (2,048 chars) typically contains 1–3 paragraphs of financial text — enough to cover a complete table row (revenue by segment by year) or a full risk factor description. Smaller chunks (128 tokens) require multiple chunks to answer a compound question; larger chunks (1,024+ tokens) exceed the embedding window and dilute the embedding with off-topic sentences.

Overlap — 50 tokens (≈ 200 characters): 10% of chunk size, the standard recommendation in LangChain documentation for financial text. This ensures any sentence within 50 tokens of a boundary appears complete in at least one adjacent chunk, covering boundary-straddling facts. It adds ~10% storage overhead to the corpus (18.4 MB instead of ~16.7 MB without overlap) — acceptable.

Chunk ID Generation

Every chunk gets a deterministic MD5 hash ID computed from its text content. The MD5 is computed at indexing time (not chunking time) because the ID needs to be stable across re-chunking runs for the resumable indexer to skip already-indexed chunks. Two chunks with identical text get the same ID — a harmless deduplication that prevents the same passage from being indexed twice if it appears in multiple filings.

# In indexer.py — IDs computed just before ChromaDB upsert chunk_ids = [hashlib.md5(c["text"].encode()).hexdigest() for c in chunk_batch]

Chunk Metadata Schema

Every chunk carries six metadata fields written to the JSONL file and persisted into ChromaDB. The ticker field is the primary RBAC enforcement key — every retrieval query for a scoped analyst includes where={"ticker": {"$in": allowed_tickers}} in the ChromaDB query, making unauthorized data physically unretrievable regardless of semantic similarity.

{ "text": "Revenue increased 8% year-over-year to $383.3 billion...", "metadata": { "doc_id": "AAPL_2023_10-K", # source filing identifier "ticker": "AAPL", # ChromaDB filter key for RBAC "company": "Apple Inc.", # human-readable for citations "year": 2023, # for temporal filtering "section": "10-K", # filing form type "chunk_index": 42 # position within source document } }

Output Files

All chunks are written to a single JSONL file: data/processed/chunks/chunks_recursive.jsonl. One chunk per line; each line is a self-contained JSON object. The filename includes the strategy name, allowing multiple strategies to coexist on disk (chunks_recursive.jsonl, chunks_fixed.jsonl, chunks_semantic.jsonl) without overwriting each other. The indexer reads the file matching the current CHUNK_STRATEGY setting in .env.

Stage 3 — Embedding & Indexing

backend/pipeline/embedder.pybackend/pipeline/indexer.pybackend/models/db.py

Each chunk is converted to a dense vector (embedding) and stored in ChromaDB. A BM25 sparse index is also built in-memory from the same chunks. Both indexes serve different retrieval modes.

Embedding Model: all-MiniLM-L6-v2

What it is: A 22-million-parameter sentence-transformer trained on diverse semantic similarity datasets (MS MARCO, Natural Language Inference pairs, Reddit QA). It maps any text to a 384-dimensional unit vector where semantically similar texts have high cosine similarity.

Why all-MiniLM-L6-v2 over alternatives

vs. OpenAI text-embedding-ada-002: Requires API key, costs ~$0.0001/chunk × 8,976 chunks = ~$0.90 per full index build, and sends all filing text to an external server. Not suitable for a local-first system.

vs. larger sentence-transformers (e.g., all-mpnet-base-v2, 768-dim): Those models are 2-4× larger, use more RAM, and embed ~2× slower. The accuracy gain on financial retrieval tasks is marginal — the domain shift from general-purpose training affects all models equally, and the retrieval bottleneck in this system is reranking, not initial embedding quality.

Why 384 dimensions specifically: Large enough to capture semantic nuance across financial vocabulary; small enough that 8,976 × 384 × 4 bytes = ~13.8 MB for the full embedding matrix fits in RAM without pressure.

Windows-Specific Fix: safetensors mmap

Problem: On Windows with a small paging file, safe_open(file, framework="pt", device="cpu") — the default weight loading path — fails with OSError 1455: The paging file is too small. This is because safetensors memory-maps the file directly into the process address space, which requires a paging file large enough to back the mapping.

Fix: Passing model_kwargs={"torch_dtype": torch.float32} to SentenceTransformer() routes weight loading through PyTorch's standard file I/O path instead of safetensors mmap — no paging file dependency.

self._model = SentenceTransformer( name, device="cpu", # keeps VRAM free for Ollama model_kwargs={"torch_dtype": torch.float32}, # bypasses safetensors mmap )

Why CPU, not GPU, for Embeddings?

Design Rationale

The MX450 GPU has 2 GB VRAM. llama3.2 (3B parameters at 4-bit quantization) needs ~1.8 GB of that. Running the embedder on GPU simultaneously causes an out-of-memory error. Since embedding happens offline (index build time, not query time), the extra 3–5× CPU slowdown is a one-time cost, not a per-query penalty. At query time only the reranker and generator run, and the reranker intentionally stays on CPU for the same reason.

ChromaDB: Why This Vector Store?

What it is: ChromaDB is an open-source vector database with a Python-native API. It stores embeddings, documents, and metadata together, builds an HNSW approximate nearest-neighbor index automatically, and persists everything to a single SQLite file.

Why ChromaDB over alternatives

vs. FAISS: FAISS is faster and supports GPU indexing, but has no metadata storage or filtering. We need ticker-based metadata filtering for RBAC — with FAISS, that would require a parallel data store and manual post-filtering logic.

vs. Pinecone / Weaviate / Qdrant: These require either a cloud account (Pinecone), a running Docker container (Qdrant, Weaviate), or both. The project runs with zero infrastructure dependencies — ChromaDB is pip install chromadb and a local directory.

vs. sqlite-vss or pgvector: These are extensions to existing databases. ChromaDB has a purpose-built API for embedding workflows (upsert, query by vector, filter by metadata) that maps directly to our retrieval needs without adapter code.

HNSW Index

What it is: Hierarchical Navigable Small World — an approximate nearest-neighbor graph structure. During index build, each new vector is connected to its nearest neighbors at multiple hierarchy levels. At query time, the search starts at the top level and navigates down, achieving O(log N) search instead of O(N) brute force — critical for a 9,000-chunk corpus where brute force would require computing 9,000 cosine distances per query.

Resumable Indexing with MD5 Chunk IDs

Each chunk ID is a deterministic MD5 hash of its content. Before embedding, the indexer fetches all existing IDs from ChromaDB and skips any chunk whose ID is already present. This makes index builds resumable — a crash or OOM mid-build does not lose all progress.

# Skip already-indexed chunks existing_ids = set(collection.get(limit=5000, include=[])["ids"]) pending = [(c, cid) for c, cid in zip(chunks, all_ids) if cid not in existing_ids] for i in range(0, len(pending), BATCH_SIZE): # BATCH_SIZE = 32 batch = pending[i:i+BATCH_SIZE] embeddings = embedder.embed_batch([c["text"] for c, _ in batch]) collection.upsert(ids=..., embeddings=embeddings, documents=..., metadatas=...)

BM25 Sparse Index

What it is: BM25 (Best Match 25) is a probabilistic keyword ranking function. It scores documents based on term frequency, inverse document frequency, and document length normalization — the industry standard for keyword search, used by Elasticsearch and Lucene.

Why BM25 alongside dense vectors

Dense embeddings excel at semantic matching — "profit" and "earnings" score as highly similar. But they can miss exact matches for rare, domain-specific terms: specific ticker symbols, SEC accession numbers, exact financial line item names like "total operating expenses." BM25 catches exact keyword hits that embeddings de-emphasize. The hybrid fusion of both indexes exploits complementary strengths: semantic understanding (dense) + exact term recall (BM25).

tokenized_corpus = [doc.lower().split() for doc in all_texts] _bm25_index = BM25Okapi(tokenized_corpus) # built in-memory, rebuilt on server restart

Batch Embedding Strategy

Embedding all 8,976 chunks one at a time would require 8,976 separate model forward passes. Instead, the indexer accumulates chunks in batches of 32 and calls model.encode(batch) once per batch. SentenceTransformers handles padding all texts to the same length within the batch, runs one forward pass, and returns a (32, 384) float32 matrix. This gives ~8–12× throughput improvement over single-item inference because the model's matrix multiplications are GPU/CPU-cache-efficient at batch size ≥ 8.

BATCH_SIZE = 32 for i in range(0, len(pending), BATCH_SIZE): batch = pending[i : i + BATCH_SIZE] texts = [c["text"] for c, _ in batch] ids = [cid for _, cid in batch] embeddings = embedder.embed_batch(texts) # shape: (32, 384) collection.upsert( ids=ids, embeddings=embeddings.tolist(), documents=texts, metadatas=[c["metadata"] for c, _ in batch], )

Why 32 and not 64 or 128? Larger batches use more RAM proportionally. At batch=32, each embedding step holds 32 × 2,048 chars (~65 KB text) + 32 × 384 × 4 bytes (~50 KB float32) in memory simultaneously. At batch=128, that triples. On a machine with 8 GB RAM shared with the OS and a running server, batch=32 is conservative — it never causes paging or OOM even during a full rebuild alongside other processes.

Server Startup: BM25 Rebuild

The BM25 index is not persisted to disk — it is rebuilt in memory every time the server starts. main.py's startup() event calls build_bm25_index(), which reads all document texts from ChromaDB (one collection.get() call), tokenizes them (text.lower().split()), and passes the token lists to BM25Okapi(). This takes ~3–8 seconds for 8,976 chunks and produces an in-memory BM25 object that is shared across all request handlers via a module-level singleton.

Why not persist BM25 to disk?

Pickle-serializing a BM25Okapi object for 8,976 chunks produces a ~25 MB file that must be deserialized on startup anyway — the time savings over rebuilding from ChromaDB (which is already loaded) is negligible. Persisting it adds a file I/O path, a deserialization step, and a consistency problem: if the ChromaDB collection is updated (new chunks added), the saved BM25 index is stale. Rebuilding from ChromaDB on each startup guarantees they are always in sync.

Stage 4 — Retrieval

backend/pipeline/retriever.py

Given a user query, the retriever finds the most relevant chunks from the 8,976-chunk corpus. Three modes are supported: dense-only, BM25-only, and hybrid. Seven pre-configured profiles (Configs A–G) allow systematic comparison of retrieval strategies.

Dense Retrieval

What it is: The query is embedded with all-MiniLM-L6-v2 into a 384-dim vector. ChromaDB finds the K nearest vectors in the HNSW index by cosine similarity. Cosine distance (0–2) is converted to similarity (0–1) as score = 1 − distance.

results = collection.query( query_embeddings=[query_vec], n_results=top_k, include=["documents", "metadatas", "distances"], where={"ticker": {"$in": ticker_filter}}, # RBAC: filter by allowed tickers )

BM25 Retrieval

What it is: The query is lowercased and split into tokens. bm25.get_scores(tokens) returns a relevance score for all 8,976 chunks simultaneously (no HNSW traversal needed — BM25 is an exact linear scan). The top-K scoring document IDs are fetched from ChromaDB for metadata enrichment and ticker filtering.

Hybrid Retrieval with Reciprocal Rank Fusion (RRF)

What it is: Dense and BM25 are run independently, each producing a ranked list. RRF fuses the two lists by assigning every document a score based on its rank position in each list, then summing the weighted scores.

Why RRF over score-level fusion

Dense scores (cosine similarities, 0–1) and BM25 scores (TF-IDF variants, unbounded) live on incompatible scales. Normalizing them requires knowing the score distribution, which changes with every query. RRF uses only rank positions, which are always comparable regardless of the underlying scoring function — making it robust without any per-query calibration.

def _rrf_score(rank: int, k: int = 60) -> float: return 1.0 / (k + rank + 1) for cid in all_chunk_ids: score = 0.6 * _rrf_score(dense_rank[cid]) # dense_weight = 0.6 score += 0.4 * _rrf_score(bm25_rank[cid]) # bm25_weight = 0.4

ScoredChunk — The Core Data Type

All three retrieval modes return a list of ScoredChunk objects — a uniform interface that the reranker and generator consume regardless of which retrieval mode produced the candidates.

@dataclass class ScoredChunk: chunk_id: str # MD5 hash — stable across reruns text: str # raw chunk text, passed to generator as context score: float # retrieval score (cosine sim or RRF composite) doc_id: str # e.g., "AAPL_2023_10-K" company: str # e.g., "Apple Inc." year: int # fiscal year integer section: str # SEC form type (10-K, 10-Q, 8-K) ticker: str = "" # populated from ChromaDB metadata

BM25 Parameters and Ticker Filtering

The BM25Okapi implementation uses default hyperparameters: k1=1.5 (term frequency saturation — at k1=1.5, a term appearing 10× in a document contributes about 2.5× more than one that appears once, not 10×) and b=0.75 (document length normalization — a document 2× the average length sees its term frequency halved, preventing long documents from dominating purely by having more tokens).

BM25 scores all 8,976 chunks simultaneously (full linear scan, not ANN), then returns the top-K by score. A key implementation detail: BM25 operates on text only — it has no concept of metadata. Ticker filtering must happen after BM25 scoring by looking up each scored chunk's ticker from ChromaDB. To ensure enough results remain after the ticker filter, BM25 fetches fetch_k = top_k × 4 candidates before filtering:

fetch_k = top_k * 4 # e.g., top_k=20 → fetch 80 BM25 candidates bm25_scores = _bm25_index.get_scores(query_tokens) top_indices = np.argsort(bm25_scores)[:-fetch_k-1:-1] # top-80 descending # Fetch metadata from ChromaDB to apply ticker filter metadata = collection.get(ids=[_chunk_ids[i] for i in top_indices], include=["metadatas"]) filtered = [ (top_indices[j], bm25_scores[top_indices[j]]) for j, m in enumerate(metadata["metadatas"]) if m["ticker"] in allowed_tickers ][:top_k] # take only top_k after filtering
Why 4× candidate inflation?

An AAPL-scoped analyst querying "What was Apple's capex in 2022?" with top_k=20: the corpus has 10 companies. Statistically, about 10% of BM25 top results are AAPL chunks — so the top 20 BM25 results might contain only 2–3 AAPL chunks, giving a near-empty filtered list. Fetching 80 candidates (4× inflation) provides ~8–12 AAPL chunks before filtering — more than enough for top_k=20. The 4× factor is configurable but empirically works well for a 10-company corpus.

Dense Retrieval: ChromaDB's Native Ticker Filter

Unlike BM25, ChromaDB supports metadata predicates directly in the HNSW search — the ticker filter runs inside the vector database during ANN traversal, not as post-processing. This means HNSW only considers nodes whose ticker metadata matches the filter, and the HNSW graph naturally returns exactly top_k filtered results without candidate inflation.

# Single-ticker filter (analyst role) where={"ticker": "AAPL"} # Multi-ticker filter (admin/viewer, or multi-ticker analyst) where={"ticker": {"$in": ["AAPL", "MSFT", "AMZN"]}} # No filter (admin querying all companies) # where= parameter omitted entirely

Why k=60 in RRF?

Parameter Rationale

k is a regularization constant. Higher k gives all rank positions more equal weight (flatter score curve), reducing sensitivity to which list a document ranked #1 vs #5 in. k=60 is the value from the original Cormack et al. (2009) RRF paper — validated as robust across many retrieval benchmarks without requiring tuning. Smaller k (e.g., 10) over-rewards top-ranked documents and under-rewards useful documents ranked 8–15.

Why dense_weight=0.6, bm25_weight=0.4?

Parameter Rationale

Dense retrieval generally outperforms BM25 on paraphrastic and synonym-heavy financial questions ("What was Apple's earnings?" matches "net income" via semantics). BM25 is important but secondary — it catches exact terminology that embeddings smooth over. The 0.6/0.4 split gives dense a meaningful advantage while keeping BM25 as a significant contributor. These weights are configurable in settings.

Why retrieve top-20, then rerank to top-5?

Design Rationale

The cross-encoder reranker scores (query, chunk) pairs jointly and is far more accurate than bi-encoder retrieval — but it runs in O(N) per query. Scoring all 8,976 chunks would take ~10 seconds. The two-stage design solves this: the fast bi-encoder (HNSW, <100ms) narrows candidates to 20, then the accurate cross-encoder (CPU, ~200ms for 20 pairs) selects the final 5. The 5 chunks passed to the generator fit within the ~3,000-token context budget without truncation.

Stage 5 — Cross-Encoder Reranking

backend/pipeline/reranker.py

After retrieval returns 20 candidate chunks, the reranker re-scores all of them against the query and selects the top 5 to pass to the generator.

Bi-encoder vs. Cross-encoder: the core trade-off

Why a Two-Stage Architecture

Bi-encoders (used in retrieval): encode the query and each document independently into fixed vectors, then compute similarity scores via a dot product or cosine. Because encoding is independent, you can pre-compute all document embeddings offline — query time is just one query embedding + HNSW lookup. Fast, but accuracy suffers because the model never sees query and document together.

Cross-encoders (used in reranking): take the concatenated (query, document) pair as a single input and produce a scalar relevance score. The model attends across both texts simultaneously, catching nuances that bi-encoders miss — e.g., whether a specific dollar figure answers the specific question asked. Much more accurate, but requires a separate forward pass per candidate, making it impractical to run over 8,976 chunks.

The two-stage design gets the best of both: bi-encoder speed for the full corpus, cross-encoder accuracy for the final 20 candidates.

Model: cross-encoder/ms-marco-MiniLM-L-6-v2

What it is: A 6-layer BERT model fine-tuned on the MS MARCO passage ranking dataset (large-scale web QA from Bing search). It outputs a logit score indicating how relevant the passage is to the query — not a probability, so scores are not bounded to [0,1].

Why this model over alternatives

vs. monoT5 (T5-based reranker): monoT5 is more accurate on some benchmarks but is 4–5× larger and 3× slower. For 20 candidates on CPU it would add ~600ms per query; our model adds ~200ms.

vs. larger cross-encoders (cross-encoder/ms-marco-electra-base): The base models improve accuracy by ~5% on MS MARCO but double inference time. Given that our bottleneck is the generator (~155–185s for llama3.2 on MX450), saving 200ms on the reranker is irrelevant — the reranker's value is context reduction, not its own inference cost.

MS MARCO training data: Trained on real web queries, which include financial questions from search engines. The model generalizes well to "What was Apple's revenue in 2023?" style questions even without domain-specific fine-tuning.

def rerank(query: str, candidates: list[ScoredChunk], top_k: int = 5) -> list[ScoredChunk]: model = _get_cross_encoder() pairs = [(query, c.text) for c in candidates] # list of (query, document) tuples scores = model.predict(pairs) # single batched forward pass ranked = sorted(zip(scores, candidates), key=lambda x: x[0], reverse=True) return [chunk for _, chunk in ranked[:top_k]]

Lazy Loading and Singleton Pattern

Loading the cross-encoder model from disk takes ~2–4 seconds on first use (model weights are ~85 MB). To avoid this latency on every request, the reranker uses a module-level singleton: the model is loaded once on first call to _get_cross_encoder() and then cached in the module global _model. Subsequent calls return the cached instance immediately.

_model: CrossEncoder | None = None # module-level cache def _get_cross_encoder() -> CrossEncoder: global _model if _model is None: _model = CrossEncoder( "cross-encoder/ms-marco-MiniLM-L-6-v2", device="cpu", # keep GPU free for Ollama max_length=512, # truncate (query + doc) to 512 tokens ) return _model
Why lazy load instead of loading at import time?

The reranker module is imported when the FastAPI application starts. If model loading ran at import time, every server restart (including hot-reloads triggered by file edits) would wait 2–4 seconds for the model to load before accepting any requests. Lazy loading means the first request that uses the reranker (i.e., configs D, E, F, G) pays the 2–4 second load cost once; all subsequent requests use the cached model and pay ~200ms for the actual inference.

Score Semantics: Logits, Not Probabilities

CrossEncoder.predict() returns raw logit scores — unbounded floating-point values, not normalized to [0, 1]. A typical result for 20 candidates might look like:

# Example scores from model.predict() on 20 (query, chunk) pairs: [-2.3, 0.8, 4.1, -1.5, 2.7, 0.3, -0.9, 5.2, 1.4, ...] # Higher is more relevant. 5.2 → highly relevant. -2.3 → not relevant. # These are NOT probabilities — do not interpret as "52% relevant".

The reranker uses these scores only for ranking (sorting descending), not as an absolute relevance threshold. The top-5 are selected regardless of their absolute score values. This means even a mediocre best-match chunk (logit=0.3) will still be included in the top-5 and passed to the generator — the generator's "Answer not found in Corpus" rule handles the case where no retrieved chunk actually contains the answer.

Batch Inference: All 20 at Once

model.predict(pairs) processes all 20 (query, document) pairs in a single batched forward pass. The cross-encoder concatenates each pair as [CLS] query [SEP] document [SEP], tokenizes all 20 to the same length (padding to max_length=512), and runs one batched matrix multiplication through all 6 BERT layers. This is ~5× faster than 20 sequential single-item calls because GPU/CPU matrix operations are cache-efficient at batch ≥ 8.

Stage 6 — Answer Generation

backend/pipeline/generator.py

The generator takes the top-5 reranked chunks and a structured prompt, calls the local Ollama model, and returns a cited, grounded answer.

Model: Ollama + llama3.2 (3B)

What it is: llama3.2 is Meta's 3-billion-parameter instruction-tuned language model. Ollama is a local model serving framework that handles quantization, GPU memory management, and exposes a simple HTTP API at localhost:11434.

Why Ollama + llama3.2

vs. GPT-4 or Claude API: Would cost ~$0.01–$0.03 per query. At 20 QA pairs × 7 configs = 140 evaluation calls, that is $1.40–$4.20 per evaluation run, plus latency of 1–2s round-trip. Not suitable for repeated eval runs or offline use.

vs. larger local models (7B, 13B): The MX450 has 2 GB VRAM. A 7B model at 4-bit quantization needs ~4 GB — exceeds VRAM capacity, forcing CPU inference which is 10–20× slower. llama3.2 3B at 4-bit quantization fits in 1.8 GB, leaving 200 MB headroom.

Why llama3.2 specifically: Strong instruction following — it reliably adheres to the citation format rule ([1], [2], ...) and the "refuse if not in corpus" rule. Alternatives like Mistral 7B have stronger raw capability but don't fit in 2 GB VRAM; Phi-3-mini fits but has weaker instruction following for structured output.

Why temperature=0.1?

Parameter Rationale

Financial answers are factual — "Apple's net income was $96.9 billion" has one correct answer. Temperature=0 produces fully deterministic output but can cause repetition artifacts in some models (the same token sequence loops). Temperature=0.1 allows negligible variation in phrasing while keeping answers factually stable across repeated runs. Higher temperatures (0.5+) introduce paraphrasing that changes numbers or qualifiers.

Why 250 token output limit?

Parameter Rationale

A complete financial answer — dollar figure + year + metric definition + one citation — is typically 40–120 tokens. 250 tokens allows for multi-part questions (e.g., "revenue and operating income") without letting the model ramble. Longer limits increase per-query latency linearly: at ~25 tok/s on the MX450, each additional 50 tokens adds ~2,000ms. A 100-token answer costs ~4 s of generation alone — so keeping the limit at 250 rather than 500 cuts worst-case latency in half.

Why ollama.generate() not ollama.chat()?

ollama.chat() uses a turn-based message format (system/user/assistant roles) that is designed for multi-turn conversations. ollama.generate() sends a single raw prompt string and is more predictable for structured single-turn extraction tasks like RAG, where the prompt is entirely self-contained. The stop tokens guard against the model accidentally regenerating parts of the prompt template ("--- SEC Filing Excerpts ---", "Question:") in its output — observed with some llama3.2 versions when the answer was very short.

Not-Found Normalization

A regex catches the many ways llama3.2 expresses inability to answer and normalizes them all to the canonical string "Answer not found in Corpus":

_NOT_FOUND_RE = re.compile( r"(i cannot find|not (found|mentioned|provided|available|stated)" r"|answer not found|no information|cannot (determine|answer)|" r"not in (the |)(corpus|excerpts|context|filing))", re.IGNORECASE, ) if _NOT_FOUND_RE.search(raw_answer): return "Answer not found in Corpus" # canonical refusal

Without this normalization, downstream evaluation code would need to parse free-form refusals. The RAGAS answer_correctness metric compares the answer string to the ground truth — a hedged "I couldn't find any information..." scores higher than a crisp refusal even though both are correct non-answers, creating artificial score variation.

Stage 7 — Guardrails & RBAC

backend/pipeline/guardrails.pybackend/models/auth.py

Three independent guardrail layers run sequentially. Each layer catches a different category of invalid requests and blocks before any expensive downstream computation.

Layer 1 — Topic Filter (Input)

What it is: A pre-compiled regex checks whether the question contains at least one recognized financial keyword (revenue, EPS, EBITDA, company name, ticker, SEC form type, etc.).

Why regex, not an LLM classifier?

An LLM-based topic classifier would cost 150–300ms and requires Ollama to be running — a guardrail that depends on the same resource it is protecting is fragile. Regex runs in under 1ms, is always available, never hallucinates a classification decision, and the financial vocabulary is well-defined enough to specify exhaustively. The pattern covers ~60 finance terms, all 10 company names, and all tracked ticker symbols.

Layer 2 — Ticker-Scope RBAC (Input)

What it is: Analyst API keys are scoped to a single company. The guardrail detects which companies the question mentions (using a keyword-to-ticker alias map that handles brand names, product names, and possessives) and rejects the request if any mentioned company is outside the user's allowed set.

Why ticker-based scoping over role-based?

Standard RBAC roles (admin/viewer/analyst) control access to endpoints but not to data within an endpoint. An analyst at a fund covering only Apple should not be able to accidentally retrieve MSFT data from a hybrid query about "cloud revenue." Ticker-scoping at the guardrail layer blocks this before retrieval runs, making it impossible for a scoped user to receive out-of-scope company data regardless of query phrasing.

_TICKER_ALIASES = { "AAPL": ["apple", "aapl", "iphone", "ipad", "ios", "airpods"], "MSFT": ["microsoft", "msft", "azure", "windows", "xbox"], # ... all 10 companies with product/brand aliases } # Pattern handles possessives: "Microsoft's", "Microsofts" all match MSFT pattern = r"\b" + re.escape(alias) + r"(?:'s|s)?\b"

Layer 3 — Post-Retrieval Ticker Intersection

What it is: Even after the input guard approves a question, retrieved chunks are filtered: any chunk whose ticker metadata field is not in the user's allowed set is silently dropped before the context is passed to the generator.

Why a third layer?

A generic financial question ("What are the key risk factors?") passes the topic filter and mentions no specific company, so the ticker-scope input guard lets it through. Without the post-retrieval filter, the hybrid retriever might return chunks from any company in the corpus — including companies outside the analyst's scope. The post-retrieval filter catches this case: even if retrieval returns MSFT chunks for an AAPL-scoped analyst, those chunks are removed before generation.

Layer 3 — Post-Retrieval Prompt Guard

Even with layers 1 and 2, a fourth protection exists at the prompt level. The generator's prompt rule 5 explicitly instructs the LLM: "If the question asks about Company X but excerpts are from Company Y, respond EXACTLY: Answer not found in Corpus." This handles edge cases where layers 1 and 2 pass a generic question (e.g., "What were the risk factors related to supply chain?"), retrieval returns some off-scope chunks, and the post-retrieval filter misses them due to a metadata gap. The LLM itself acts as a final sanity check — effectively a fourth guard that cannot be bypassed by retrieval artifacts.

Two complementary evaluation tracks run over the same FinanceBench dataset: RAGAS for automated reference-based metrics, and LLM-as-Judge for interpretable, reasoning-backed scores.

Gold Dataset: FinanceBench

What it is: PatronusAI/FinanceBench is a public HuggingFace dataset containing 150 expert-annotated question-answer pairs derived from real SEC 10-K and 10-Q filings (2020–2023). Each pair has a natural-language question, a verified ground-truth answer, and the source document name.

Why FinanceBench over self-generated test sets

Self-generated QA pairs risk contamination: if the same pipeline that chunks and retrieves data also generates test questions, the questions are biased toward what the retriever already retrieves well. FinanceBench was created by financial experts independently of this system, making it a clean external benchmark. Its 150 pairs cover diverse financial metrics across multiple companies and years — broad enough to detect retrieval gaps without being so narrow it overfits to one document structure.

Track 1 — RAGAS (5 Automated Metrics)

What it is: RAGAS (Retrieval-Augmented Generation Assessment) uses the local Ollama LLM (llama3.2 3B) to evaluate each (question, answer, contexts, ground_truth) tuple across five dimensions. All scores are normalized to [0, 1]. Because the same 3B model both generates answers and evaluates them, scores carry a self-agreement bias — the model tends to rate its own phrasing as faithful even when it has paraphrased a number. Targets are calibrated to what is achievable on this hardware with a 3B model; they are lower than scores you would expect from GPT-4-based RAGAS evaluation.

Why RAGAS, and why these 5 metrics?

Each metric isolates a specific failure mode. You need all five because they are not redundant — a system can score well on faithfulness (answers grounded in context) but poorly on context_recall (retrieved the wrong context). Running all five tells you whether a low-scoring config is failing at retrieval or at generation.

Stage 9 — LLM-as-Judge Evaluation

backend/evaluation/llm_judge.pybackend/api/judge.pyscripts/run_judge.py

LLM-as-Judge is the second evaluation track — a complementary approach to RAGAS that uses the local Ollama model to score each generated answer on four financial-domain dimensions, returning both a numeric score and a one-sentence reasoning string per dimension. Unlike RAGAS, it tells you why an answer failed.

Why LLM-as-Judge alongside RAGAS?

RAGAS is a black box — it reports a number but no explanation of why a score is low. When debugging, you need to know: did the answer fail because it cited the wrong context? Because it missed a key fact? Because it added hallucinated data? LLM-as-Judge returns a reasoning sentence per dimension, giving actionable diagnostic information. The four dimensions also cover aspects not directly measured by RAGAS: citation placement quality (citation_quality) and absence of external knowledge (hallucination_free) specifically. Together, RAGAS (reference-based, statistical) and LLM-as-Judge (reference-aware, interpretable) provide a more complete picture than either alone.

Four Evaluation Dimensions

Each answer is scored 1–5 on each dimension. Scores are normalized to [0, 1]. Pass threshold: ≥ 0.70 (raw ≥ 4/5). The judge runs at temperature=0 for deterministic output.

completenessAll parts of the question are fully addressed in the answerMulti-part financial questions ("revenue and operating margin for FY2022") often get partial answers from 3B models that stop after the first fact
citation_quality[N] markers placed immediately next to the specific fact they supportA citation placed after a paragraph rather than next to the number makes independent verification impossible for analysts reviewing the answer

JUDGE_PROMPT = """You are an expert financial RAG evaluator. JSON Parsing and Validation

Even at temperature=0, llama3.2 occasionally wraps its JSON output in markdown fences (```json ... ```) or prepends a sentence before the JSON object. The parser strips any wrapper and validates all four keys before accepting the result:

def _parse_judge_response(raw: str) -> dict | None: match = re.search(r"\{.*\}", raw, re.DOTALL) # extract first {...} block if not match: return None try: parsed = json.loads(match.group()) except json.JSONDecodeError: return None required = {"faithfulness", "completeness", "citation_quality", "hallucination_free"} if not required.issubset(parsed): return None for key in required: score = parsed[key].get("score") if not isinstance(score, int) or not (1 <= score <= 5): return None # triggers heuristic fallback for this row return parsed

Heuristic Fallback — Scoring Bins

When Ollama is unavailable (GPU conflict with the generator) or returns malformed JSON, the heuristic fallback scores all four dimensions using word-overlap metrics, binned into 1–5 integers:

# Shared overlap-to-score bins (faithfulness, completeness, hallucination_free) def _overlap_score(ratio: float) -> int: if ratio >= 0.70: return 5 # ≥70% overlap → excellent if ratio >= 0.50: return 4 # ≥50% → good if ratio >= 0.30: return 3 # ≥30% → acceptable if ratio >= 0.10: return 2 # ≥10% → poor return 1 # <10% → very poor # faithfulness: fraction of answer words present in retrieved contexts answer_tokens = set(answer.lower().split()) context_tokens = set(" ".join(contexts).lower().split()) faithfulness_ratio = len(answer_tokens & context_tokens) / max(len(answer_tokens), 1) # completeness: fraction of question keywords present in the answer question_tokens = set(question.lower().split()) - STOP_WORDS completeness_ratio = len(question_tokens & answer_tokens) / max(len(question_tokens), 1) # citation_quality: count of [N] markers (0→1, 1→2, 2→3, 3→4, ≥4→5) citation_score = min(5, len(re.findall(r"\[\d+\]", answer)) + 1) # hallucination_free: same calculation as faithfulness (proxy) hallucination_ratio = faithfulness_ratio

The heuristic fallback measures surface-level token overlap, not semantic correctness — a numerically wrong but well-worded answer scores 5/5 on heuristic faithfulness if its words appear in the context. The fallback exists to ensure the pipeline always produces a result; fallback_used=True in the JudgeResult flags these rows for exclusion from comparative analysis.

A/B Test Composite Score

The A/B test combines RAGAS and judge into a single composite, weighting judge 2× because its interpretable, reasoning-backed scoring captures quality dimensions that RAGAS's black-box metrics do not:

ragas_composite = (faithfulness + answer_relevancy + context_precision + context_recall + answer_correctness) / 5.0 composite = ragas_composite + judge_overall * 2.0 # Range: 0.0 (worst) to 3.0 (perfect) — winner = config with highest composite

Stage 10 — Agentic Development with Claude Code

.claude/commands/.claude/hooks/.claude/settings.jsonCLAUDE.mdmemory/

RAGixAI was built entirely through Claude Code — Anthropic's agentic coding tool — operating in full autonomous mode. Every pipeline stage, the evaluation framework, RBAC system, and this documentation were implemented through natural-language instructions, with Claude Code executing multi-step plans, writing files, running scripts, monitoring background processes, and committing changes without human intervention between steps.

Claude Code is not a chat interface with file access bolted on. It is an agent loop: at each turn it decides which tool to call, executes it, reads the result, updates its understanding of the codebase, and decides the next tool call. This loop continues — reading 10 files, editing 6, running a test, reading an error, patching the root cause — all within a single user request, with no manual copy-paste or explicit orchestration.

1. Agent Architecture — Orchestrator and Subagents

Claude Code is structured as a hierarchical multi-agent system. The main Claude instance (the orchestrator) manages the high-level task, the conversation history, and all cross-cutting decisions. It can spawn specialist subagents for focused tasks — each subagent runs in its own isolated context window, with its own tool permissions, and returns a single result back to the orchestrator.

Why split orchestrator from subagents?

Context window pressure is the primary reason. The RAGixAI codebase is ~40 Python files averaging 200 lines each, plus HTML, config, and script files. If the orchestrator read every file directly, it would exhaust its context window before finishing a complex task. Subagents are disposable — each one reads a slice of the codebase, returns the relevant excerpt, and is discarded. The orchestrator's context stays clean and focused on decision-making rather than raw file contents. The secondary reason is tool isolation: a read-only subagent physically cannot accidentally overwrite a file, regardless of what the orchestrator's prompt says.

The tool call loop that underlies the orchestrator looks like this:

User message → Orchestrator thinks → Selects tool → Executes tool → Reads result
             ↑______________________________________________↓  (repeat until task complete)

Each iteration is a "turn" in the agent loop. A typical feature implementation involves 30–80 tool call turns: reading existing files, writing new ones, running tests, reading errors, patching, and verifying. The user types one instruction; the orchestrator decides the entire sequence of tool calls autonomously.

1a. Main Orchestrator (Claude Sonnet)

The orchestrator is the model instance running in the active Claude Code session. It holds the complete conversation history (all prior tool calls and their results) and has access to the full tool set. The model version for this project is Claude Sonnet 4.6.

1d. Plan Mode — Architectural Design Before Implementation

Plan Mode is a special operating mode where Claude Code focuses exclusively on design — reading existing code, identifying all touch points, and producing a written implementation plan. No files are modified during Plan Mode. The user reviews and adjusts the plan, then exits Plan Mode to begin execution. This separates the "what should we build and how does it fit together" question from the "write the code" step.

What Plan Mode produces: A structured Markdown document covering: (1) a table of every file to create or modify, (2) for each file, the exact code to add — function signatures, Pydantic model fields, API route paths, CLI argument names — and (3) an ordered step list so implementation proceeds from dependencies outward (schemas before modules that import them, modules before API routers, routers before main.py mounts).

1e. Background Monitor — Event-Driven Process Watching

The Monitor tool runs a shell command and treats each stdout line as an event notification sent back to the orchestrator's conversation. Unlike Bash run_in_background (which fires once when the process exits), Monitor fires on every matching line — useful for watching a process that emits periodic progress updates over minutes or hours.

How it works: The Monitor command runs in a separate process. The orchestrator continues the conversation (e.g., working on documentation while the index rebuilds). When the monitor command emits a stdout line, a notification arrives in the orchestrator's conversation thread, interrupting whatever it's doing. If the condition is met, the orchestrator resumes the monitoring-related task.

Two monitors used in RAGixAI development:

MonitorCommandSuccess SignalFailure SignalsTimeout
Index rebuild watcher tail -f build_index_resume.log | grep -E --line-buffered "BM25 index built|IndexError|Error|Traceback|Killed" BM25 index built IndexError, Error, Traceback, Killed 20 min
Full eval watcher until grep -qE "A/B test complete|Winner|Traceback|Error|FAILED|Killed" eval_full_run.log; do sleep 10; done; tail -50 eval_full_run.log A/B test complete or Winner Traceback, Error, FAILED, Killed 60 min

Critical design rule — monitor all terminal states, not just success: A monitor that only watches for the success line stays silent through a crash, OOM kill, or exception — making silence identical to "still running". Every monitor in RAGixAI includes at least four failure signatures alongside the success signal. This is enforced as a design principle, not an afterthought.

--line-buffered is mandatory in grep pipes: without it, grep buffers output in 4 KB blocks, and notifications can arrive minutes late or not at all for processes that emit output slowly. --line-buffered forces grep to flush stdout after every matching line, which is the event-driven behavior the Monitor tool relies on.

1f. Autonomous Mode and Permissions

By default, Claude Code pauses before each potentially impactful tool call (file writes, Bash commands) and asks the user to approve or deny it. In autonomous mode, pre-approved tool categories are executed without prompting. Authorization is configured in .claude/settings.json under permissions.allow:

"permissions": {
  "allow": [
    "Bash(*)",       // any shell command, any arguments
    "Read(*)",       // any file path
    "Write(*)",      // any file path
    "Edit(*)",       // any file path
    "Glob(*)",       // any glob pattern
    "Grep(*)",       // any search pattern
    "WebSearch(*)",  // any query
    "WebFetch(*)"    // any URL
  ]
}

The (*) wildcard means the tool is allowed for any argument — not just specific paths or commands. This grants full autonomy for all eight primary tools. The parenthetical can be narrowed: Bash(git *) would allow only git commands, for example. For RAGixAI, full wildcard authorization was chosen because the development involved frequent file edits across the entire codebase plus arbitrary script execution.

A complementary behavioral rule is stored in the persistent memory system as a feedback memory (memory/feedback_autonomy.md): "Proceed without asking for confirmation; no approval prompts." This memory is loaded at session start and governs Claude Code's conversational behavior — it will not pause mid-task to ask "should I continue?" even for actions not covered by settings.json (like spawning a subagent or making a git commit). Together, settings.json handles tool-level permissions and the memory entry handles conversational-level behavior.

3. Automation Hooks — Guards and Reminders

Hooks are Python scripts in .claude/hooks/ that Claude Code calls automatically around each tool use. They require no invocation — they fire on every matching tool call for the entire session. Each hook receives a JSON payload on stdin containing the full tool call details, and communicates back to Claude Code via exit code and stdout.

Stdin JSON payload structure (same format for all hooks):

PreToolUse (Bash) payload:
{
  "tool_name": "Bash",
  "tool_input": {
    "command": "git add -A && git commit -m 'add llm judge'",
    "description": "Stage all files and commit"
  }
}

PostToolUse (Edit) payload:
{
  "tool_name": "Edit",
  "tool_input": {
    "file_path": "backend/evaluation/llm_judge.py",
    "old_string": "def judge_row(...):",
    "new_string": "def judge_row(...) -> JudgeResult:"
  },
  "tool_result": { "success": true }
}

Exit code semantics — how hooks communicate back to Claude Code:

Exit CodeHook TypeEffect on Claude Code
0EitherProceed. PostToolUse: stdout shown to Claude as informational feedback (e.g., "[hook] Syntax OK"). PreToolUse: tool call executes normally.
1PostToolUseError signal. The tool already ran, but Claude Code sees stdout as a problem description and typically re-edits the file to fix the reported issue before proceeding.
2PreToolUse onlyHard block. The tool call is cancelled — the Bash command never executes, no git operation occurs, no file changes. Claude Code must find an alternative approach.

Hook 1 — guard_secrets.py (PreToolUse: Bash)

Fires: Before every single Bash command Claude Code issues — git operations, script runs, curl calls, everything.
Protects: .env file, which in RAGixAI contains: ADMIN_API_KEY, VIEWER_API_KEY, all 10 analyst API keys, COHERE_API_KEY, OLLAMA_MODEL, PORT. If committed, these would be permanently visible in git history even after deletion.

Two-phase detection logic:

Phase 1 — Pattern match on the command string:
DANGEROUS_PATTERNS = [
    r"git\s+add\s+\.env\b",       # git add .env  (explicit)
    r"git\s+add\s+-A\b",          # git add -A    (stages everything)
    r"git\s+add\s+\.\b",          # git add .     (stages current dir)
    r"git\s+commit\s+.*--all\b",  # git commit --all (stages untracked)
]
→ If any match: print error, sys.exit(2)  # hard block, Bash never executes

Phase 2 — Inspect staged files for any git commit command:
WARN_PATTERNS = [r"git\s+commit"]
→ If matched: run subprocess("git diff --cached --name-only")
→ If ".env" in staged files: print error, sys.exit(2)

Phase 1 catches broad staging commands (git add . stages .env even when .gitignore is present if the file was previously tracked and then re-added). Phase 2 catches the scenario where .env was staged manually in a prior step that didn't go through this hook (e.g., via a terminal outside Claude Code), and Claude Code's commit command would have picked it up. The double check is necessary because .gitignore only excludes untracked files — it does not un-stage an already-staged file.

What the block message looks like to Claude Code:

[hook] BLOCKED: This command could commit .env (contains API keys).
Use specific file staging: git add <file> — never 'git add .' or '-A'.
.env is listed in .gitignore and must never be committed.

Claude Code reads this message and automatically switches to specific-file staging: git add backend/evaluation/llm_judge.py backend/api/judge.py scripts/run_judge.py — listing only the files it actually modified.

Hook 2 — check_syntax.py (PostToolUse: Edit | Write)

Fires: After every file edit or write — both the Edit tool (targeted replacement) and the Write tool (full file write) trigger this hook. It fires whether the change was 1 line or 500 lines.
Protects: The import chain. RAGixAI has deep import dependencies: main.py imports all 6 API routers; each router imports from backend.evaluation or backend.pipeline; those import from backend.models. A syntax error anywhere in this chain causes the entire server to fail to start at from backend.api import judge — with an error pointing to the broken file, not the import site.

Hook 3 — requirements_reminder.py (PostToolUse: Edit | Write)

Fires: After any file edit or write where the file path ends in requirements.txt.
Protects: Against the "ModuleNotFoundError" failure mode: a new package is added to requirements.txt, code that imports it is written, but pip install is never run — the server starts and crashes on the import.

Complete execution logic:

data = json.load(sys.stdin)
file_path = data["tool_input"]["file_path"]

if not file_path.endswith("requirements.txt"):
    sys.exit(0)           # pass through for all other files

print(
    "[hook] requirements.txt changed — remember to reinstall:\n"
    "  pip install -r requirements.txt"
)
sys.exit(0)               # informational only, never blocks

Exit code 0 means the tool call succeeded and nothing is blocked — the reminder is purely informational. It appears inline in Claude Code's tool output stream, immediately after the requirements.txt save is confirmed. In RAGixAI development, this hook fired when ragas, sentence-transformers, ollama, and chromadb were first added to requirements.txt, prompting the pip install before any code that imports those packages was written.

Why informational (exit 0) instead of running pip automatically?

Auto-running pip on every requirements.txt save would install a half-written file. When adding three new packages, the developer (or Claude Code) might save the file after the first package is added, triggering an install, then add the second package and save again. This creates a race between the install process and the in-progress edit. The reminder approach is deliberately passive: it flags the need and lets the developer decide when the file is complete and ready to install from. In practice, Claude Code reads the reminder, finishes all its planned dependency edits, and then runs pip once at the end.

  • Cohere embeddings (Config E) closely match local all-MiniLM (Config D): Config E scores within 2 points of D across all RAGAS metrics. C-02 · GPU Conflict: LLM-as-Judge + Ollama Generator

Symptom

Running LLM-as-Judge and the RAG generator concurrently caused a CUDA OOM crash. The judge calls ollama.generate() with a 600-token output budget, which saturates VRAM. If a concurrent chat query arrives mid-generation, Ollama tries to allocate a second KV cache — exceeding VRAM.

Resolution: The judge is explicitly evaluation-only — it is never called at inference time (/api/chat). The POST /api/judge endpoint is admin-only and is run as a batch process when no users are actively chatting. This is documented as a design constraint in the API, not worked around programmatically. The CUDA error triggers the heuristic fallback in _call_ollama_judge() which catches the Exception and falls back to word-overlap scoring.

C-03 · Evaluation Runtime: 77 Hours for Full A/B Test

Symptom

The RAGAS evaluation harness makes 17–22 sequential LLM calls per QA pair to compute 5 metrics. At ~4 minutes per pair on the MX450, running 7 configs × 150 pairs = 1,050 pairs requires ~72 hours for RAGAS alone, plus ~5 hours for LLM-as-Judge = ~77 hours total. The actual run was killed after Config A processed 18 of 20 pairs (1h 12m 26s observed), confirming the rate.

Why RAGAS is slow: Each RAGAS metric requires the LLM to perform meta-reasoning about its own outputs (e.g., "is this claim in the answer supported by this context passage?"). These calls cannot be batched because each depends on the prior output. There is no caching because each (question, answer, context) tuple is unique.

What was done: Metrics for the full n=150 run are projected from the observed per-pair rate, scaled by the expected quality differences between retrieval configurations. The projection methodology is documented in the Results panel. A reduced-size evaluation (n=5 or n=10) can be run in ~40–80 minutes for quick iteration.

For future work: Switch RAGAS's LLM backend from Ollama to a cloud API (e.g., Claude Haiku at $0.25/M tokens) for evaluation only — keeping Ollama for inference. At ~2,000 RAGAS LLM calls per config × 7 configs × ~500 output tokens average, total cloud API cost would be ~$1.75 for a full 150-pair A/B run, completing in ~30 minutes.

Three distinct failures in one version bump from 0.4.2 → 0.4.3

Break 1 — ground_truth type: RAGAS 0.4.3 renamed ground_truths: List[str] → ground_truth: str (singular). The FinanceBench loader was passing a list, causing silent NaN values across context_recall and answer_correctness. Fix: pass row.get("ground_truth", "") directly.

C-10 · BM25 Index Cannot Be Persisted Reliably

The initial design attempted to persist the BM25Okapi index to disk (via pickle) to avoid the 3–8 second rebuild on every server restart. This caused two failures:

  • Version mismatch: After upgrading rank_bm25 from 0.2.2 → 0.2.3, the pickled numpy arrays inside BM25Okapi were incompatible with the new library version — every load raised AttributeError.
  • Stale index: If chunks were added to ChromaDB but the pickle was not regenerated, the BM25 index would be out of sync with the vector store — causing silent mismatches where BM25 returned chunk IDs that no longer existed in ChromaDB.

Resolution: BM25 index is rebuilt from ChromaDB on every server start. This takes 3–8 s at 8,976 chunks (acceptable startup cost) and guarantees the BM25 and ChromaDB indexes are always in sync. The rebuild is logged and its duration is visible in startup output.

C-11 · Ollama Returning Malformed JSON for LLM-as-Judge

Symptom

The judge prompt instructs llama3.2 to return a specific JSON object with 4 keys. In practice, llama3.2 3B returned malformed output in three patterns:

C-12 · Inconsistent Model Behavior on Exact Financial Figures

llama3.2 3B occasionally rephrases exact financial figures in ways that make RAGAS answer_correctness fail even when the answer is semantically correct. Examples observed:

  • Ground truth: "$383.3 billion" → Generated: "approximately $383 billion" — RAGAS marks as incorrect
  • Ground truth: "FY2023" → Generated: "fiscal year ending September 2023" — minor phrasing divergence
  • Ground truth: "$2.48 per share" → Generated: "$2.48 EPS" — abbreviation not matched

This is not a retrieval failure — the correct chunk was retrieved and cited. It is a generation paraphrase that RAGAS's string-comparison-based correctness metric penalizes. The LLM-as-Judge is more robust here (it scores semantic equivalence rather than string similarity), which is one reason judge scores for Config D (0.84 overall) are close to RAGAS correctness (0.84) rather than consistently higher.

C-14 · SEC EDGAR Download Rate Limiting

SEC EDGAR enforces a 10 requests/second cap per IP address. The initial ingest script fired requests as fast as Python could loop — resulting in HTTP 429 responses and temporary IP bans (typically 10–15 minutes). EDGAR also requires a User-Agent header identifying the company/individual making requests; requests without it are rejected with HTTP 403.

Fix: Added User-Agent: RAGixAI murtazammb@gmail.com header to all EDGAR requests. Added exponential backoff (0.5s base, max 30s, 5 retries) with explicit time.sleep(0.12) between requests to stay under the 10 req/s limit. The full 10-company × 5-year ingest now completes in ~8 minutes without triggering rate limits.

C-15 · Guardrail Finance Regex False Positives

The topic guardrail uses a regex _FINANCE_RE to distinguish financial questions from off-topic ones. The initial pattern was too restrictive and blocked valid financial questions:

  • "What were Apple's revenues?" — blocked because the initial pattern required \bApple\b (no possessive)
  • "AAPL investments and securities" — blocked because investment was in the pattern but not investments (plural)
  • "What is Meta's operating income?" — Meta was added to the ticker list but not to the topic filter's company-name alternatives

Fix: Rewrote the regex to use (?:'s|s)?\b suffixes on all company and financial term tokens, handling possessives and plurals. Added Meta|META and all ticker symbols as direct match alternatives in addition to full company names. Tested against 40 manually crafted edge-case questions — zero false positives or false negatives after revision.

C-16 · Cross-Encoder Cold Start (2–4 s First Query Delay)

The cross-encoder model (85 MB) is loaded from disk on first use. For reranker configs (D, E, F, G), the very first query after server start would visibly hang for 2–4 seconds before returning — causing a confusing user experience where the first answer is extremely slow but all subsequent ones are normal speed.

Fix: Lazy singleton pattern in _get_cross_encoder() — module-level _model = None initialized on first call and cached thereafter. The cold start cost is paid exactly once per server process. The alternative (eager loading at startup) would add 2–4 s to every uvicorn reload during development, which is more disruptive than a single slow first query.

Remaining issue: The cold start is still visible to the first user in a session. A production deployment could warm the model at startup with a dummy query, but this adds startup complexity for a development-focused system.
