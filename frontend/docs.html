RAGixAI — Technical Documentation

A deep-dive into every design decision: what each component is, why it was chosen over alternatives, and how each piece fits the overall system.

System Overview

RAGixAI is a local-first Retrieval-Augmented Generation system over SEC EDGAR financial filings. It takes natural-language questions about public company financials and returns precise, cited answers grounded exclusively in the retrieved filing text — not the model's training data.

Why RAG, not fine-tuning?

Design Rationale

SEC filings are published every quarter. Fine-tuning a model requires re-running full training whenever data changes — expensive (requires A100-class GPUs) and slow (days of training). RAG separates the knowledge store from the model: adding new filings means updating ChromaDB, not retraining anything. Fine-tuned models also hallucinate financial numbers with high confidence because they interpolate training data; RAG anchors every answer to retrieved text and enforces citation, making hallucinations detectable and refutable.

Why local-first?

Design Rationale

Financial analysis workflows often involve sensitive internal context even when the filings themselves are public. Running entirely on-device eliminates data egress, removes per-token API costs, and avoids internet dependency during inference. The entire stack (embedder, reranker, generator, vector store) runs on consumer hardware — a laptop GPU with 2 GB VRAM is sufficient.

Stage 1 — Data Ingestion

backend/pipeline/ingest.pyscripts/run_ingest.py

The ingestion layer downloads SEC regulatory filings directly from the SEC EDGAR REST API, extracts plain text, and writes each document with structured metadata to disk.

What is SEC EDGAR?

EDGAR (Electronic Data Gathering, Analysis, and Retrieval) is the SEC's public filing database. Every US-listed public company must submit financial disclosures here. The API at data.sec.gov provides programmatic access to filing indices and full document text with no authentication required.

Why the EDGAR API directly?

Design Rationale

Primary reason: freshness and completeness. HuggingFace financial datasets (e.g., FinancialPhraseBank, EDGAR-CORPUS) are static snapshots. New quarterly filings never appear in them. Going directly to EDGAR means we can always fetch the latest 10-Q the day it is filed. It also gives us full document text — not excerpts — which is critical for retrieval coverage. The SEC's rate limit is 10 requests/second, well within what a batch ingest process needs.

Filing Types and Why Each Matters

CIK Number Registry

Every EDGAR filer has a unique Central Index Key (CIK). These are hardcoded in the ingester since they never change for an established company. The CIK is zero-padded to 10 digits for API calls.

TICKER_TO_CIK = { "AAPL": "320193", "MSFT": "789019", "AMZN": "1018724", "GOOGL": "1652044", "META": "1326801", "NVDA": "1045810", "TSLA": "1318605", "JPM": "19617", "BAC": "70858", "WMT": "104169", } # Request header required by SEC — identifies the application and contact EDGAR_HEADERS = {"User-Agent": "RAGixAI capstone murtazammb@gmail.com"}

Download Flow

  1. Fetch data.sec.gov/submissions/CIK{id}.json — returns full filing history with form types, accession numbers, dates
  2. Filter by form type (10-K, 10-Q, 8-K) and target year range
  3. Fetch filing index from sec.gov/Archives/edgar/data/{cik}/{accession}/
  4. Extract the primary document (largest .txt or .htm file in the filing package)
  5. Strip HTML tags, normalize whitespace, write to data/raw/edgar/{TICKER}_{year}_{form}.txt
  6. Append structured metadata to data/raw/edgar/manifest.json for downstream stages

Rate limiting: A time.sleep(0.15) between requests keeps us at ~6 req/s — well below the 10 req/s SEC limit. Exceeding it causes a 429 block for ~15 minutes.

Stage 2 — Document Chunking

backend/pipeline/chunker.pyscripts/run_chunk.py

A 10-K filing is 80–200 pages of dense text — far too large to embed or include in any LLM context. Chunking splits documents into overlapping segments that are small enough to embed and retrieve individually while retaining enough context to answer a question.

Why overlapping chunks?

Design Rationale

A key financial fact (e.g., a revenue figure) often appears at a sentence boundary. Without overlap, that sentence might be split across two chunks and appear in neither fully. An overlap of 50 tokens ensures that any sentence near a boundary appears complete in at least one chunk, improving retrieval recall without duplicating much text.

Chunking Strategy: Recursive Character (default)

What it is: LangChain's RecursiveCharacterTextSplitter splits text using a priority hierarchy of separators: paragraph breaks (\n\n) first, then line breaks (\n), then sentence ends (. ), then word boundaries ( ), and finally character-level splits as a last resort. It never splits mid-sentence unless there is no other option.

Why Recursive over Fixed-Size or Semantic

vs. Fixed-Size: Fixed-size chunking (splitting at exactly N tokens using tiktoken) frequently bisects sentences mid-word because it has no concept of linguistic structure. A financial sentence like "Net income increased 23% to $29.7 billion" split in half loses context from both halves. Recursive splitting preserves sentence and paragraph integrity whenever the text allows it.

vs. Semantic: Semantic chunking embeds every sentence and inserts boundaries where cosine similarity drops below a threshold. It produces the most topically coherent chunks but is ~10× slower (requires a forward pass per sentence) and produces variable-length chunks that are harder to reason about. For a 9,000-chunk corpus built once, the extra build time is acceptable — but the unpredictable chunk sizes make retrieval less stable. Recursive chunking gives consistent ~512-token chunks with good linguistic quality.

class RecursiveCharChunker: separators = ["\n\n", "\n", ". ", " ", ""] # tried in order chunk_size = 512 * 4 # ≈ 2048 chars ≈ 512 tokens (4 chars/token heuristic) chunk_overlap = 50 * 4 # ≈ 200 chars ≈ 50 tokens overlap

Why 512 tokens / 50-token overlap?

Parameter Rationale

Chunk size 512 tokens: all-MiniLM-L6-v2 has a 256-token maximum input window. Chunks at ~512 tokens (estimated via the 4 chars/token heuristic) are typically ~400–480 actual tokens — within the model's window while containing enough text to carry a complete financial disclosure (one paragraph to one table row). Smaller chunks (128–256 tokens) increase recall but reduce the coherence of each chunk; larger chunks (1024+) exceed the model window and dilute the embedding with off-topic content.

Overlap 50 tokens: This is ~10% of the chunk size — the standard recommendation in the LangChain documentation for financial text. It ensures boundary sentences appear whole in at least one chunk without duplicating more than 10% of the corpus.

Chunk Metadata Schema

Every chunk carries four metadata fields persisted in ChromaDB. The ticker field is the primary RBAC filter key — every retrieval query for a scoped analyst filters on this field.

{ "text": "Revenue increased 8% year-over-year to $383.3 billion...", "metadata": { "doc_id": "AAPL_2023_10K", "ticker": "AAPL", # used for RBAC filtering at retrieval "year": 2023, "section": "10-K", "chunk_index": 42 } }

Stage 3 — Embedding & Indexing

backend/pipeline/embedder.pybackend/pipeline/indexer.pybackend/models/db.py

Each chunk is converted to a dense vector (embedding) and stored in ChromaDB. A BM25 sparse index is also built in-memory from the same chunks. Both indexes serve different retrieval modes.

Embedding Model: all-MiniLM-L6-v2

What it is: A 22-million-parameter sentence-transformer trained on diverse semantic similarity datasets (MS MARCO, Natural Language Inference pairs, Reddit QA). It maps any text to a 384-dimensional unit vector where semantically similar texts have high cosine similarity.

Why all-MiniLM-L6-v2 over alternatives

vs. OpenAI text-embedding-ada-002: Requires API key, costs ~$0.0001/chunk × 8,976 chunks = ~$0.90 per full index build, and sends all filing text to an external server. Not suitable for a local-first system.

vs. larger sentence-transformers (e.g., all-mpnet-base-v2, 768-dim): Those models are 2-4× larger, use more RAM, and embed ~2× slower. The accuracy gain on financial retrieval tasks is marginal — the domain shift from general-purpose training affects all models equally, and the retrieval bottleneck in this system is reranking, not initial embedding quality.

Why 384 dimensions specifically: Large enough to capture semantic nuance across financial vocabulary; small enough that 8,976 × 384 × 4 bytes = ~13.8 MB for the full embedding matrix fits in RAM without pressure.

Windows-Specific Fix: safetensors mmap

Problem: On Windows with a small paging file, safe_open(file, framework="pt", device="cpu") — the default weight loading path — fails with OSError 1455: The paging file is too small. This is because safetensors memory-maps the file directly into the process address space, which requires a paging file large enough to back the mapping.

Fix: Passing model_kwargs={"torch_dtype": torch.float32} to SentenceTransformer() routes weight loading through PyTorch's standard file I/O path instead of safetensors mmap — no paging file dependency.

self._model = SentenceTransformer( name, device="cpu", # keeps VRAM free for Ollama model_kwargs={"torch_dtype": torch.float32}, # bypasses safetensors mmap )

Why CPU, not GPU, for Embeddings?

Design Rationale

The MX450 GPU has 2 GB VRAM. llama3.2 (3B parameters at 4-bit quantization) needs ~1.8 GB of that. Running the embedder on GPU simultaneously causes an out-of-memory error. Since embedding happens offline (index build time, not query time), the extra 3–5× CPU slowdown is a one-time cost, not a per-query penalty. At query time only the reranker and generator run, and the reranker intentionally stays on CPU for the same reason.

ChromaDB: Why This Vector Store?

What it is: ChromaDB is an open-source vector database with a Python-native API. It stores embeddings, documents, and metadata together, builds an HNSW approximate nearest-neighbor index automatically, and persists everything to a single SQLite file.

Why ChromaDB over alternatives

vs. FAISS: FAISS is faster and supports GPU indexing, but has no metadata storage or filtering. We need ticker-based metadata filtering for RBAC — with FAISS, that would require a parallel data store and manual post-filtering logic.

vs. Pinecone / Weaviate / Qdrant: These require either a cloud account (Pinecone), a running Docker container (Qdrant, Weaviate), or both. The project runs with zero infrastructure dependencies — ChromaDB is pip install chromadb and a local directory.

vs. sqlite-vss or pgvector: These are extensions to existing databases. ChromaDB has a purpose-built API for embedding workflows (upsert, query by vector, filter by metadata) that maps directly to our retrieval needs without adapter code.

HNSW Index

What it is: Hierarchical Navigable Small World — an approximate nearest-neighbor graph structure. During index build, each new vector is connected to its nearest neighbors at multiple hierarchy levels. At query time, the search starts at the top level and navigates down, achieving O(log N) search instead of O(N) brute force — critical for a 9,000-chunk corpus where brute force would require computing 9,000 cosine distances per query.

Resumable Indexing with MD5 Chunk IDs

Each chunk ID is a deterministic MD5 hash of its content. Before embedding, the indexer fetches all existing IDs from ChromaDB and skips any chunk whose ID is already present. This makes index builds resumable — a crash or OOM mid-build does not lose all progress.

# Skip already-indexed chunks existing_ids = set(collection.get(limit=5000, include=[])["ids"]) pending = [(c, cid) for c, cid in zip(chunks, all_ids) if cid not in existing_ids] for i in range(0, len(pending), BATCH_SIZE): # BATCH_SIZE = 32 batch = pending[i:i+BATCH_SIZE] embeddings = embedder.embed_batch([c["text"] for c, _ in batch]) collection.upsert(ids=..., embeddings=embeddings, documents=..., metadatas=...)

BM25 Sparse Index

What it is: BM25 (Best Match 25) is a probabilistic keyword ranking function. It scores documents based on term frequency, inverse document frequency, and document length normalization — the industry standard for keyword search, used by Elasticsearch and Lucene.

Why BM25 alongside dense vectors

Dense embeddings excel at semantic matching — "profit" and "earnings" score as highly similar. But they can miss exact matches for rare, domain-specific terms: specific ticker symbols, SEC accession numbers, exact financial line item names like "total operating expenses." BM25 catches exact keyword hits that embeddings de-emphasize. The hybrid fusion of both indexes exploits complementary strengths: semantic understanding (dense) + exact term recall (BM25).

tokenized_corpus = [doc.lower().split() for doc in all_texts] _bm25_index = BM25Okapi(tokenized_corpus) # built in-memory, rebuilt on server restart

Stage 4 — Retrieval

backend/pipeline/retriever.py

Given a user query, the retriever finds the most relevant chunks from the 8,976-chunk corpus. Three modes are supported: dense-only, BM25-only, and hybrid. Seven pre-configured profiles (Configs A–G) allow systematic comparison of retrieval strategies.

Dense Retrieval

What it is: The query is embedded with all-MiniLM-L6-v2 into a 384-dim vector. ChromaDB finds the K nearest vectors in the HNSW index by cosine similarity. Cosine distance (0–2) is converted to similarity (0–1) as score = 1 − distance.

results = collection.query( query_embeddings=[query_vec], n_results=top_k, include=["documents", "metadatas", "distances"], where={"ticker": {"$in": ticker_filter}}, # RBAC: filter by allowed tickers )

BM25 Retrieval

What it is: The query is lowercased and split into tokens. bm25.get_scores(tokens) returns a relevance score for all 8,976 chunks simultaneously (no HNSW traversal needed — BM25 is an exact linear scan). The top-K scoring document IDs are fetched from ChromaDB for metadata enrichment and ticker filtering.

Hybrid Retrieval with Reciprocal Rank Fusion (RRF)

What it is: Dense and BM25 are run independently, each producing a ranked list. RRF fuses the two lists by assigning every document a score based on its rank position in each list, then summing the weighted scores.

Why RRF over score-level fusion

Dense scores (cosine similarities, 0–1) and BM25 scores (TF-IDF variants, unbounded) live on incompatible scales. Normalizing them requires knowing the score distribution, which changes with every query. RRF uses only rank positions, which are always comparable regardless of the underlying scoring function — making it robust without any per-query calibration.

def _rrf_score(rank: int, k: int = 60) -> float: return 1.0 / (k + rank + 1) for cid in all_chunk_ids: score = 0.6 * _rrf_score(dense_rank[cid]) # dense_weight = 0.6 score += 0.4 * _rrf_score(bm25_rank[cid]) # bm25_weight = 0.4

Why k=60 in RRF?

Parameter Rationale

k is a regularization constant. Higher k gives all rank positions more equal weight (flatter score curve), reducing sensitivity to which list a document ranked #1 vs #5 in. k=60 is the value from the original Cormack et al. (2009) RRF paper — validated as robust across many retrieval benchmarks without requiring tuning. Smaller k (e.g., 10) over-rewards top-ranked documents and under-rewards useful documents ranked 8–15.

Why dense_weight=0.6, bm25_weight=0.4?

Parameter Rationale

Dense retrieval generally outperforms BM25 on paraphrastic and synonym-heavy financial questions ("What was Apple's earnings?" matches "net income" via semantics). BM25 is important but secondary — it catches exact terminology that embeddings smooth over. The 0.6/0.4 split gives dense a meaningful advantage while keeping BM25 as a significant contributor. These weights are configurable in settings.

Why retrieve top-20, then rerank to top-5?

Design Rationale

The cross-encoder reranker scores (query, chunk) pairs jointly and is far more accurate than bi-encoder retrieval — but it runs in O(N) per query. Scoring all 8,976 chunks would take ~10 seconds. The two-stage design solves this: the fast bi-encoder (HNSW, <100ms) narrows candidates to 20, then the accurate cross-encoder (CPU, ~200ms for 20 pairs) selects the final 5. The 5 chunks passed to the generator fit within the ~3,000-token context budget without truncation.

Stage 5 — Cross-Encoder Reranking

backend/pipeline/reranker.py

After retrieval returns 20 candidate chunks, the reranker re-scores all of them against the query and selects the top 5 to pass to the generator.

Bi-encoder vs. Cross-encoder: the core trade-off

Why a Two-Stage Architecture

Bi-encoders (used in retrieval): encode the query and each document independently into fixed vectors, then compute similarity scores via a dot product or cosine. Because encoding is independent, you can pre-compute all document embeddings offline — query time is just one query embedding + HNSW lookup. Fast, but accuracy suffers because the model never sees query and document together.

Cross-encoders (used in reranking): take the concatenated (query, document) pair as a single input and produce a scalar relevance score. The model attends across both texts simultaneously, catching nuances that bi-encoders miss — e.g., whether a specific dollar figure answers the specific question asked. Much more accurate, but requires a separate forward pass per candidate, making it impractical to run over 8,976 chunks.

The two-stage design gets the best of both: bi-encoder speed for the full corpus, cross-encoder accuracy for the final 20 candidates.

Model: cross-encoder/ms-marco-MiniLM-L-6-v2

What it is: A 6-layer BERT model fine-tuned on the MS MARCO passage ranking dataset (large-scale web QA from Bing search). It outputs a logit score indicating how relevant the passage is to the query — not a probability, so scores are not bounded to [0,1].

Why this model over alternatives

vs. monoT5 (T5-based reranker): monoT5 is more accurate on some benchmarks but is 4–5× larger and 3× slower. For 20 candidates on CPU it would add ~600ms per query; our model adds ~200ms.

vs. larger cross-encoders (cross-encoder/ms-marco-electra-base): The base models improve accuracy by ~5% on MS MARCO but double inference time. Given that our bottleneck is the generator (1–3s for llama3.2), saving 200ms on the reranker is not worth the accuracy trade-off in the other direction.

MS MARCO training data: Trained on real web queries, which include financial questions from search engines. The model generalizes well to "What was Apple's revenue in 2023?" style questions even without domain-specific fine-tuning.

def rerank(query: str, candidates: list[ScoredChunk], top_k: int = 5) -> list[ScoredChunk]: model = _get_cross_encoder() pairs = [(query, c.text) for c in candidates] # list of (query, document) tuples scores = model.predict(pairs) # single batched forward pass ranked = sorted(zip(scores, candidates), key=lambda x: x[0], reverse=True) return [chunk for _, chunk in ranked[:top_k]]

GPU strategy: The reranker runs on CPU to keep the MX450's 2 GB VRAM exclusively for Ollama's llama3.2 inference. CrossEncoder at 85 MB on CPU adds ~200ms — acceptable latency given that Ollama generation takes 1–3s.

Stage 6 — Answer Generation

backend/pipeline/generator.py

The generator takes the top-5 reranked chunks and a structured prompt, calls the local Ollama model, and returns a cited, grounded answer.

Model: Ollama + llama3.2 (3B)

What it is: llama3.2 is Meta's 3-billion-parameter instruction-tuned language model. Ollama is a local model serving framework that handles quantization, GPU memory management, and exposes a simple HTTP API at localhost:11434.

Why Ollama + llama3.2

vs. GPT-4 or Claude API: Would cost ~$0.01–$0.03 per query. At 20 QA pairs × 7 configs = 140 evaluation calls, that is $1.40–$4.20 per evaluation run, plus latency of 1–2s round-trip. Not suitable for repeated eval runs or offline use.

vs. larger local models (7B, 13B): The MX450 has 2 GB VRAM. A 7B model at 4-bit quantization needs ~4 GB — exceeds VRAM capacity, forcing CPU inference which is 10–20× slower. llama3.2 3B at 4-bit quantization fits in 1.8 GB, leaving 200 MB headroom.

Why llama3.2 specifically: Strong instruction following — it reliably adheres to the citation format rule ([1], [2], ...) and the "refuse if not in corpus" rule. Alternatives like Mistral 7B have stronger raw capability but don't fit in 2 GB VRAM; Phi-3-mini fits but has weaker instruction following for structured output.

Why temperature=0.1?

Parameter Rationale

Financial answers are factual — "Apple's net income was $96.9 billion" has one correct answer. Temperature=0 produces fully deterministic output but can cause repetition artifacts in some models (the same token sequence loops). Temperature=0.1 allows negligible variation in phrasing while keeping answers factually stable across repeated runs. Higher temperatures (0.5+) introduce paraphrasing that changes numbers or qualifiers.

Why 250 token output limit?

Parameter Rationale

A complete financial answer — dollar figure + year + metric definition + one citation — is typically 40–120 tokens. 250 tokens allows for multi-part questions (e.g., "revenue and operating income") without letting the model ramble. Longer limits increase per-query latency linearly: each additional 50 tokens adds ~200ms on the MX450.

Prompt Design

The prompt enforces five hard constraints. Each constraint addresses a specific failure mode observed in initial testing:

Rules you MUST follow: 1. Cite every fact with [1], [2], etc. # prevents uncited hallucination 2. If not found, say: "Answer not found in Corpus" # clean refusal over hedging 3. Do NOT use knowledge from outside the excerpts # blocks training-data leakage 4. Do NOT speculate or infer # prevents educated guessing 5. If excerpts are from Company X but question asks about Y, refuse # cross-company guard

Context Block: Why Include Source Metadata?

Each chunk is formatted with its source document and relevance score:

[1] (Source: Apple 2023 10-K, relevance: 0.91) Revenue increased 8% year-over-year to $383.3 billion...

Showing the source document name and year lets the model include temporal context in its citation ("per the 2023 10-K [1]") without hallucinating dates. The relevance score helps the model prioritize — in practice it cites higher-relevance chunks more consistently when the scores are visible in the prompt.

Not-Found Normalization

A regex catches the many ways llama3.2 expresses inability to answer ("I cannot find...", "is not mentioned in...", "not provided in the excerpts") and normalizes them all to the canonical string "Answer not found in Corpus". This prevents partial answers where the model hedges with "I couldn't fully confirm but..." instead of refusing cleanly.

Stage 7 — Guardrails & RBAC

backend/pipeline/guardrails.pybackend/models/auth.py

Three independent guardrail layers run sequentially. Each layer catches a different category of invalid requests and blocks before any expensive downstream computation.

Layer 1 — Topic Filter (Input)

What it is: A pre-compiled regex checks whether the question contains at least one recognized financial keyword (revenue, EPS, EBITDA, company name, ticker, SEC form type, etc.).

Why regex, not an LLM classifier?

An LLM-based topic classifier would cost 150–300ms and requires Ollama to be running — a guardrail that depends on the same resource it is protecting is fragile. Regex runs in under 1ms, is always available, never hallucinates a classification decision, and the financial vocabulary is well-defined enough to specify exhaustively. The pattern covers ~60 finance terms, all 10 company names, and all tracked ticker symbols.

_FINANCE_RE = re.compile( r"\b(revenue|profit|loss|earn(?:ing|ings)?|eps|ebitda|margin|" r"income|expense|cash\s*flow|balance\s*sheet|asset|liabilit|equit|" r"sec|10-?k|10-?q|8-?k|quarterly|filing|fiscal|" r"apple|microsoft|amazon|google|alphabet|meta|nvidia|tesla|jpmorgan|" r"aapl|msft|amzn|googl|nvda|tsla|jpm|walmart|bank\s+of\s+america|" # ... 25 more terms r")(?:'s|s)?\b", re.IGNORECASE )

Layer 2 — Ticker-Scope RBAC (Input)

What it is: Analyst API keys are scoped to a single company. The guardrail detects which companies the question mentions (using a keyword-to-ticker alias map that handles brand names, product names, and possessives) and rejects the request if any mentioned company is outside the user's allowed set.

Why ticker-based scoping over role-based?

Standard RBAC roles (admin/viewer/analyst) control access to endpoints but not to data within an endpoint. An analyst at a fund covering only Apple should not be able to accidentally retrieve MSFT data from a hybrid query about "cloud revenue." Ticker-scoping at the guardrail layer blocks this before retrieval runs, making it impossible for a scoped user to receive out-of-scope company data regardless of query phrasing.

_TICKER_ALIASES = { "AAPL": ["apple", "aapl", "iphone", "ipad", "ios", "airpods"], "MSFT": ["microsoft", "msft", "azure", "windows", "xbox"], # ... all 10 companies with product/brand aliases } # Pattern handles possessives: "Microsoft's", "Microsofts" all match MSFT pattern = r"\b" + re.escape(alias) + r"(?:'s|s)?\b"

Layer 3 — Post-Retrieval Ticker Intersection

What it is: Even after the input guard approves a question, retrieved chunks are filtered: any chunk whose ticker metadata field is not in the user's allowed set is silently dropped before the context is passed to the generator.

Why a third layer?

A generic financial question ("What are the key risk factors?") passes the topic filter and mentions no specific company, so the ticker-scope input guard lets it through. Without the post-retrieval filter, the hybrid retriever might return chunks from any company in the corpus — including companies outside the analyst's scope. The post-retrieval filter catches this case: even if retrieval returns MSFT chunks for an AAPL-scoped analyst, those chunks are removed before generation.

Stage 8 — Evaluation Framework

backend/evaluation/ragas_eval.pybackend/evaluation/llm_judge.pybackend/evaluation/ab_test.pybackend/evaluation/financebench_loader.py

Two complementary evaluation tracks run over the same FinanceBench dataset: RAGAS for automated reference-based metrics, and LLM-as-Judge for interpretable, reasoning-backed scores.

Gold Dataset: FinanceBench

What it is: PatronusAI/FinanceBench is a public HuggingFace dataset containing 150 expert-annotated question-answer pairs derived from real SEC 10-K and 10-Q filings (2020–2023). Each pair has a natural-language question, a verified ground-truth answer, and the source document name.

Why FinanceBench over self-generated test sets

Self-generated QA pairs risk contamination: if the same pipeline that chunks and retrieves data also generates test questions, the questions are biased toward what the retriever already retrieves well. FinanceBench was created by financial experts independently of this system, making it a clean external benchmark. Its 150 pairs cover diverse financial metrics across multiple companies and years — broad enough to detect retrieval gaps without being so narrow it overfits to one document structure.

Track 1 — RAGAS (5 Automated Metrics)

What it is: RAGAS (Retrieval-Augmented Generation Assessment) uses the local Ollama LLM to evaluate each (question, answer, contexts, ground_truth) tuple across five dimensions. All scores are normalized to [0, 1].

Why RAGAS, and why these 5 metrics?

Each metric isolates a specific failure mode. You need all five because they are not redundant — a system can score well on faithfulness (answers grounded in context) but poorly on context_recall (retrieved the wrong context). Running all five tells you whether a low-scoring config is failing at retrieval or at generation.

MetricTargetWhat It DetectsFailure Mode Caught
faithfulness≥ 0.89Every claim in the answer is supported by retrieved contextGenerator hallucinating facts not in the retrieved chunks
answer_relevancy≥ 0.87Answer directly addresses what was askedAnswer is factual but off-topic (answers a different question)
context_precision≥ 0.84Retrieved chunks are relevant to the questionRetriever returning noisy, off-topic chunks
context_recall≥ 0.84Retrieved chunks cover all facts needed to answerRetriever missing relevant chunks (incomplete recall)
answer_correctness≥ 0.82Answer matches the ground truthAnswer is grounded and relevant but numerically wrong

RAGAS 0.4.3 on Windows — three breaking changes fixed:
(1) RAGAS_DO_NOT_TRACK=1 — analytics module spawns a subprocess at import time without a if __name__ == "__main__" guard, causing recursive process spawn and crash on Windows.
(2) ground_truth field must be a singular string, not a list — changed between 0.1.x and 0.4.x.
(3) EvaluationResult[key] returns List[float], not a scalar — use np.nanmean() to aggregate.

Track 2 — LLM-as-Judge (4 Domain-Specific Dimensions)

What it is: The local Ollama model scores each generated answer at temperature=0 on four dimensions, returning both a numeric score (1–5) and a one-sentence reasoning string per dimension. Scores are normalized to [0, 1]. Pass threshold is 0.70 (≥ 4/5 raw score).

Why LLM-as-Judge alongside RAGAS?

RAGAS is a black box — it reports a number but no explanation of why a score is low. When debugging, you need to know: did the answer fail because it cited the wrong context? Because it missed a key fact? Because it added hallucinated data? LLM-as-Judge returns a reasoning sentence per dimension, giving actionable diagnostic information. The four dimensions also cover aspects not directly measured by RAGAS: citation placement quality (citation_quality) and absence of external knowledge (hallucination_free) specifically. Together, RAGAS (reference-based, statistical) and LLM-as-Judge (reference-aware, interpretable) provide a more complete picture than either alone.

DimensionDefinitionWhy Financial RAG Specifically Needs This
faithfulnessEvery factual claim traceable to retrieved contextsFinancial numbers cannot be approximated — a hallucinated revenue figure is wrong by definition even if close
completenessAll parts of the question fully addressedMulti-part financial questions ("revenue and operating margin") often get partial answers
citation_quality[N] markers placed next to the specific fact they supportA citation after the paragraph rather than next to the number makes verification impossible for analysts
hallucination_freeNo external knowledge beyond retrieved contextsLLMs have memorized financial data from training — they can produce correct-looking but corpus-external numbers

Heuristic Fallback

When Ollama is unavailable or returns malformed JSON, a word-overlap heuristic replaces the LLM judge. Faithfulness and hallucination_free use answer/context token overlap; completeness uses question keyword presence in answer; citation_quality counts [N] markers in the response. Scores bin into 1–5 using fixed overlap thresholds. This ensures the evaluation pipeline always produces a result.

A/B Test and Winner Selection

All 7 configs run sequentially. Winner is determined by a composite score: ragas_faithfulness + ragas_relevancy + judge_overall × 2 — the judge is weighted 2× because it is more interpretable and domain-specific than the automated RAGAS metrics.

Why FastAPI?

Design Rationale

vs. Flask: Flask lacks native async support and has no Pydantic integration — request validation requires manual boilerplate. FastAPI generates OpenAPI documentation automatically from type hints, which is critical for team API exploration during development.

vs. Django REST Framework: Too heavyweight for a focused microservice. Django's ORM, admin panel, and authentication system are not needed here and would add complexity without benefit.

Native Pydantic v2: Request and response schemas are Python dataclasses with type annotations. FastAPI validates them automatically — a malformed request body never reaches pipeline code.

Why SQLite for Session History?

Design Rationale

Session history (chat turns, timestamps, config used) needs to persist across server restarts and support simple queries (fetch last N sessions for a user). SQLite satisfies this with zero infrastructure: no database server, no connection pool, no configuration. For a single-tenant local application with low concurrency, SQLite's write serialization is not a bottleneck. A production multi-tenant deployment would migrate to PostgreSQL, but that migration is trivial with SQLAlchemy.

Stage 10 — Agentic Development with Claude Code

RAGixAI was built entirely through Claude Code — Anthropic's agentic coding tool — operating in full autonomous mode. Every pipeline stage, the evaluation framework, RBAC system, and this documentation were implemented through natural-language instructions with Claude Code executing multi-step plans, writing files, running tests, and committing changes.

Why Claude Code for development?

Design Rationale

Multi-file autonomous execution: Features like LLM-as-Judge span 6+ files (schema, core module, API router, main.py, CLI script, A/B test integration). Claude Code implements all of them in sequence without human copy-paste between files — it reads existing code, understands dependencies, and maintains consistency across the entire change set.

Live debugging: When errors occurred (HNSW corruption, Windows mmap OOM, RAGAS API changes), Claude Code diagnosed by reading log files, forming hypotheses, and applying targeted fixes — often within the same session that discovered the error.

Plan mode: Complex features were designed in Plan Mode, producing a file-by-file implementation plan with exact code sketches before any file was modified. This prevented architectural mistakes that would have required large rewrites.
