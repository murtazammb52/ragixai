A comprehensive reference covering every layer of the RAGixAI implementation: data ingestion through evaluation, API design, security, and agentic development methodology.

System Overview

RAGixAI is a local-first Retrieval-Augmented Generation (RAG) system purpose-built for SEC EDGAR financial filings. It answers natural-language questions about 10-K, 10-Q, and 8-K reports with precise, cited answers grounded exclusively in corpus evidence — no hallucinated external knowledge.

Design philosophy: Everything runs on-device. No paid API calls during inference. The full pipeline — embedding, retrieval, reranking, and generation — runs on consumer hardware using free-tier models (sentence-transformers + CrossEncoder + Ollama/llama3.2).

Gold Evaluation Dataset — FinanceBench

Evaluation uses PatronusAI/FinanceBench, a public HuggingFace dataset containing 150 expert-annotated QA pairs derived from real SEC 10-K and 10-Q filings (2020–2023). Each pair includes a natural-language question, a ground-truth answer, and the source document name. This provides an objective, external benchmark that does not overfit to self-generated test data.

Fallback: If the HuggingFace dataset is unavailable, the loader falls back to 30 hardcoded QA pairs covering all 10 companies (2020–2023) embedded in backend/evaluation/financebench_loader.py.

Stage 1 — Data Ingestion

RAGixAI ingests SEC filings directly from the SEC EDGAR REST API (data.sec.gov) — no third-party datasets or HuggingFace dependencies for the primary corpus. The ingestion layer resolves company tickers to CIK numbers, fetches filing indices, and downloads full-text documents.

backend/pipeline/ingest.py scripts/run_ingest.py

SEC EDGAR API Integration

The EDGAR submissions endpoint returns a structured JSON manifest of all filings for a given CIK:

# CIK registry — 10 tracked companies TICKER_TO_CIK = { "AAPL": "320193", "MSFT": "789019", "AMZN": "1018724", "GOOGL": "1652044", "META": "1326801", "NVDA": "1045810", "TSLA": "1318605", "JPM": "19617", "BAC": "70858", "WMT": "104169", } # EDGAR API header required by SEC (rate limit: 10 req/s) EDGAR_HEADERS = { "User-Agent": "RAGixAI capstone murtazammb@gmail.com", "Accept-Encoding": "gzip, deflate", } url = f"https://data.sec.gov/submissions/CIK{cik_padded}.json"

Filing Download Flow

  1. Fetch CIK{id}.json — contains full filing history with form types, accession numbers, and dates
  2. Filter to target form types: 10-K, 10-Q, 8-K
  3. Filter by year range (--years flag, default 2020–2026)
  4. Fetch the full-text submission index from https://www.sec.gov/Archives/edgar/data/{cik}/{accession}/*.txt
  5. Extract the primary document (largest .txt or .htm file)
  6. Strip HTML tags, normalize whitespace, write to data/raw/edgar/{ticker}_{year}_{form}.txt
  7. Append to manifest JSON (data/raw/edgar/manifest.json)

Stage 2 — Document Chunking

SEC filings are multi-hundred-page documents unsuitable for direct embedding. Chunking splits them into semantically coherent segments that fit within the embedding model's context window while preserving enough context for accurate retrieval.

backend/pipeline/chunker.py scripts/run_chunk.py

Three Chunking Strategies

1 · Fixed-Size (token-boundary)

Uses tiktoken (cl100k_base encoding) to split at exact token boundaries. Fastest strategy, but may bisect sentences mid-thought.

class FixedSizeChunker(BaseChunker): chunk_size: int = 512 # tokens overlap: int = 50 # tokens of overlap between consecutive chunks enc = tiktoken.get_encoding("cl100k_base")

2 · Recursive Character (default)

Uses LangChain's RecursiveCharacterTextSplitter with a hierarchy of separators: \n\n → \n → ". " → " " → "". Respects paragraph and sentence boundaries before falling back to arbitrary splits. This is the production default because it produces cleaner, more semantically complete chunks for financial filings.

class RecursiveCharChunker(BaseChunker): separators = ["\n\n", "\n", ". ", " ", ""] chunk_size = 512 * 4 # ~2048 chars ≈ 512 tokens (4 chars/token heuristic) chunk_overlap = 50 * 4 # ~200 chars overlap

3 · Semantic (cosine similarity)

Embeds each sentence with all-MiniLM-L6-v2, then inserts a chunk boundary wherever the cosine similarity between adjacent sentence embeddings drops below 0.5. Produces the most cohesive topic chunks but is ~10× slower and requires a minimum of 3 sentences per chunk.

class SemanticChunker(BaseChunker): threshold: float = 0.5 # cosine sim below which a boundary is inserted # Splits at i if cosine(embed[i-1], embed[i]) < 0.5 AND len(current) >= 3

Chunk Metadata Schema

Every chunk carries structured metadata persisted in ChromaDB and used for RBAC filtering:

{ "text": "...filing excerpt...", "metadata": { "doc_id": "AAPL_2023_10K", "company": "Apple Inc.", "ticker": "AAPL", # RBAC filter key "year": 2023, "section": "10-K", "chunk_index": 42, "strategy": "recursive" } }

Stage 3 — Embedding & Indexing

Each chunk is embedded into a dense vector and stored in ChromaDB with an HNSW index for approximate nearest-neighbor search. A BM25 sparse index is built in-memory from the same chunks for keyword-based retrieval. Both indexes are used together in hybrid mode.

backend/pipeline/embedder.py backend/pipeline/indexer.py backend/models/db.py scripts/run_build_index.py

Embedding Model

The default embedding model is sentence-transformers/all-MiniLM-L6-v2: a 22M-parameter, 384-dimensional model optimized for semantic similarity. It runs entirely on CPU to avoid VRAM contention with the Ollama generator (which uses the GPU for llama3.2 inference).

# Windows-specific: torch.float32 dtype bypasses safetensors mmap # which fails with OSError 1455 (paging file too small) on Windows self._model = SentenceTransformer( name, device="cpu", model_kwargs={"torch_dtype": torch.float32}, )

Windows mmap fix: Without torch_dtype=float32, SentenceTransformer uses safe_open(file, framework="pt", device="cpu") which memory-maps the weight file. On Windows with a small paging file this throws OSError 1455. Specifying the dtype forces a direct load path that bypasses mmap.

Optional: Cohere Embed v3

Config E uses Cohere Embed v3 (1024-dim, English) via the Cohere free tier (1000 calls/month). When enabled, chunks are stored in a separate ChromaDB collection (ragixai_cohere) so both embedding models can coexist without interference.

# .env EMBED_MODEL=cohere COHERE_API_KEY=your-key-here # Collection: ragixai_cohere (vs ragixai_local for sentence-transformers)

ChromaDB Vector Store

ChromaDB is used as a persistent local vector database. Each chunk gets a deterministic ID derived from an MD5 hash of its content, enabling resumable indexing: if the index build is interrupted, already-indexed chunks are detected by ID comparison and skipped.

BATCH_SIZE = 32 # chunks embedded and upserted per batch # Resumable: fetch all existing IDs before the loop existing_ids = set(collection.get(limit=5000, include=[])["ids"]) pending_pairs = [(c, cid) for c, cid in zip(chunks, all_ids) if cid not in existing_ids] # Embed and upsert in batches for i in range(0, len(pending_pairs), BATCH_SIZE): batch = pending_pairs[i:i+BATCH_SIZE] embeddings = embedder.embed_batch([c["text"] for c, _ in batch]) collection.upsert(ids=..., embeddings=embeddings, documents=..., metadatas=...)

BM25 Sparse Index

After the ChromaDB build completes, a BM25Okapi index is built in-memory from all chunk texts fetched from ChromaDB. The index is not persisted to disk — it is rebuilt from ChromaDB at server startup or first retrieval request.

from rank_bm25 import BM25Okapi tokenized_corpus = [doc.lower().split() for doc in all_texts] _bm25_index = BM25Okapi(tokenized_corpus) _bm25_doc_ids = all_ids # parallel list mapping BM25 rank → ChromaDB ID

Stage 4 — Retrieval

The retrieval layer supports three modes — dense, BM25, and hybrid — and exposes seven pre-configured retrieval profiles (Config A–G) for systematic A/B testing. All modes support optional ticker filtering for RBAC enforcement.

backend/pipeline/retriever.py

Dense Retrieval

Embeds the query with all-MiniLM-L6-v2, then queries ChromaDB for the top-K nearest vectors by cosine similarity (stored as distance, converted with score = 1 − distance). Supports a ChromaDB where clause for ticker-scoped filtering.

results = collection.query( query_embeddings=[query_vec], n_results=top_k, include=["documents", "metadatas", "distances"], where={"ticker": {"$in": ticker_filter}}, # optional RBAC filter )

BM25 Retrieval

Tokenizes the query by whitespace-splitting its lowercased form, then runs bm25.get_scores(tokenized_query). The top-K document IDs are mapped back to ChromaDB metadata for ticker filtering. When ticker filtering is active, BM25 fetches top_k × 4 candidates to allow post-filter pruning while still returning top_k results.

Hybrid Retrieval (RRF Fusion)

Hybrid mode runs dense and BM25 independently, then fuses their ranked lists using Reciprocal Rank Fusion (RRF) with k=60. RRF assigns each document a score of 1 / (k + rank + 1) from each ranker, weighted by configurable coefficients.

def _rrf_score(rank: int, k: int = 60) -> float: return 1.0 / (k + rank + 1) # Default weights (from settings) dense_weight = 0.6 # heavier weight on semantic similarity bm25_weight = 0.4 # lighter weight on keyword match for cid in all_ids: score = dense_weight * _rrf_score(dense_ids[cid]) if cid in dense_ids else 0 score += bm25_weight * _rrf_score(sparse_ids[cid]) if cid in sparse_ids else 0

Stage 5 — Cross-Encoder Reranking

After retrieval returns 20 candidate chunks, a cross-encoder re-scores all (query, chunk) pairs jointly — unlike bi-encoders (used for retrieval) which encode query and document independently, the cross-encoder sees both simultaneously and produces a more accurate relevance score. The top 5 are passed to the generator.

backend/pipeline/reranker.py

Model Details

cross-encoder/ms-marco-MiniLM-L-6-v2
~85 MB · 6-layer BERT · CPU-only
Trained on MS MARCO passage ranking
Outputs scalar relevance logit per pair
Architecture: Why Cross-Encoder?
Bi-encoders (retrieval) trade accuracy for speed via independent encoding. Cross-encoders recover accuracy by attending across both sequences — at the cost of O(N) inference per query.

Implementation

def rerank(query: str, candidates: list[ScoredChunk], top_k=5) -> list[ScoredChunk]: model = _get_cross_encoder() pairs = [(query, c.text) for c in candidates] # list of (query, doc) tuples scores = model.predict(pairs) # single forward pass for all pairs ranked = sorted(zip(scores, candidates), key=lambda x: x[0], reverse=True) return [chunk for _, chunk in ranked[:top_k]]

GPU strategy: The cross-encoder runs on CPU to avoid VRAM contention with the Ollama generator (which uses the MX450's 2 GB VRAM for llama3.2 inference). Running both on GPU simultaneously causes OOM. The latency cost is ~200 ms for 20 pairs.

Stage 6 — Answer Generation

The generator takes the top-5 reranked chunks and produces a cited, grounded answer using a local Ollama instance running llama3.2 (3B). The prompt template enforces citation discipline and out-of-corpus refusal.

backend/pipeline/generator.py

Prompt Design

The prompt is structured as a strict instruction followed by numbered context excerpts. Five hard rules are injected: cite every fact, refuse if not in corpus, no external knowledge, no speculation, and company-scope enforcement. The LLM is constrained to at most 250 tokens output.

PROMPT_TEMPLATE = """You are a financial analyst assistant. Answer questions ONLY using the SEC filing excerpts provided below. Rules you MUST follow: 1. Cite every fact with [1], [2], etc. matching the excerpt numbers. 2. If the answer cannot be found, respond EXACTLY with: Answer not found in Corpus 3. Do NOT use any knowledge from outside the provided excerpts. 4. Do NOT speculate, infer, or add information not in the excerpts. 5. If the question asks about Company X but excerpts are from Company Y, respond EXACTLY with: Answer not found in Corpus --- SEC Filing Excerpts --- {context} --- End of Excerpts --- Question: {question} Answer (cite sources with [N]):"""

Context Block Construction

Each chunk is formatted with a numbered citation label, source metadata, and relevance score:

context_block = "\n\n".join([ f"[{i+1}] (Source: {c.company} {c.year} 10-K, relevance: {c.score:.2f})\n{c.text[:800]}" for i, c in enumerate(contexts) ])

Ollama Configuration

response = ollama.generate( model="llama3.2", prompt=prompt, options={"temperature": 0.1, "num_predict": 250}, )

Citation Extraction

After generation, citation indices are extracted from the response using a regex pattern r"\[(\d+)\]". Cited chunks become the citations list returned to the API and displayed in the UI. If the LLM produces no citations but didn't refuse, the first 3 retrieval results are used as implicit citations.

Not-Found Normalization

A fallback regex pattern normalizes LLM variations of "I cannot find..." into the canonical string "Answer not found in Corpus", preventing hallucinated partial answers when the LLM hedges instead of refusing cleanly.

_NOT_FOUND_RE = re.compile( r"(?:I\s+(?:cannot|can'?t|could\s+not|couldn'?t)\s+find" r"|(?:is|are|was|were)\s+not\s+(?:mentioned|found|provided|available)" # ... 5 more patterns r")", re.IGNORECASE )

Stage 7 — Guardrails & RBAC

RAGixAI enforces three independent guardrail layers: topic filtering, content moderation, and role-based access control (RBAC). Guardrails run before retrieval, minimizing unnecessary compute on blocked requests.

backend/pipeline/guardrails.py backend/models/auth.py

Layer 1 — Topic Filter

A pre-compiled regex (_FINANCE_RE) matches financial vocabulary: revenue, EPS, EBITDA, 10-K, SEC, company names, tickers, and ~40 other finance terms. Questions that match zero financial terms are rejected with a guidance message. The pattern uses (?:'s|s)?\b suffixes to handle possessives and plurals.

_FINANCE_RE = re.compile( r"\b(revenue|profit|loss|earn(?:ing|ings|ed)?|eps|ebitda|margin|" r"income|expense|cash\s*flow|balance\s*sheet|asset|liabilit|equit|" r"sec|10-?k|10-?q|8-?k|annual\s*report|quarterly|filing|" r"apple|microsoft|amazon|google|alphabet|meta|nvidia|tesla|" r"aapl|msft|amzn|googl|nvda|tsla|jpm|walmart|bank\s+of\s+america|" # ... 25 more terms r")(?:'s|s)?\b", re.IGNORECASE )

Layer 2 — Ticker-Scope RBAC

Analyst API keys are scoped to a single company. On every request, detected company mentions (via _TICKER_ALIASES keyword expansion) are compared against the user's allowed ticker set. Questions mentioning out-of-scope tickers are rejected at the guardrail level before any retrieval occurs.

_TICKER_ALIASES = { "AAPL": ["apple", "aapl", "iphone", "ipad", "airpods", "ios"], "MSFT": ["microsoft", "msft", "azure", "windows", "xbox"], "AMZN": ["amazon", "amzn", "aws", "alexa", "prime"], # ... 7 more companies with product/brand aliases } def check_ticker_scope(question, allowed_tickers): mentioned = detect_mentioned_tickers(question) # expands aliases to tickers disallowed = [t for t in mentioned if t not in allowed_tickers] if disallowed: return GuardResult(False, f"Access denied: {disallowed}")

Layer 3 — Post-Retrieval Hallucination Guard

After retrieval, any chunk whose ticker metadata does not appear in the user's allowed set is filtered from the context. This prevents a scoped analyst from receiving content from a different company via a query that bypassed the input guard (e.g., generic finance questions).

Stage 8 — Evaluation Framework

RAGixAI uses a dual-track evaluation framework: RAGAS for automated, reference-based metrics and LLM-as-Judge for interpretable, domain-aware scoring. Both tracks run over FinanceBench (150 expert QA pairs) and support all seven retrieval configurations for systematic A/B comparison.

backend/evaluation/ragas_eval.py backend/evaluation/llm_judge.py backend/evaluation/ab_test.py backend/evaluation/financebench_loader.py scripts/run_evaluate.py scripts/run_judge.py scripts/run_ab_test.py

Track 1 — RAGAS Automated Metrics

RAGAS (v0.4.3) evaluates each (question, answer, contexts, ground_truth) tuple on five dimensions using the local Ollama LLM as the evaluating model. All metrics are normalized to [0, 1].

MetricTargetMeasures
faithfulness≥ 0.89Every claim in the answer is supported by retrieved context
answer_relevancy≥ 0.87Answer directly addresses the question asked
context_precision≥ 0.84Retrieved chunks are on-topic (no noise)
context_recall≥ 0.84Retrieved chunks cover all relevant facts
answer_correctness≥ 0.82Factual accuracy vs. ground truth answer

RAGAS 0.4.3 Windows compatibility fixes applied:
(1) RAGAS_DO_NOT_TRACK=1 prevents analytics from spawning a subprocess that crashes Windows without a if __name__ == "__main__" guard.
(2) ground_truth must be a singular string (not a list) in 0.4.x.
(3) EvaluationResult[key] returns List[float] — use np.nanmean().
(4) Import singletons from ragas.metrics._faithfulness (not .collections).

Track 2 — LLM-as-Judge

The judge calls the local Ollama model at temperature=0 to score each answer on four financial-RAG-specific dimensions, returning a numeric score (1–5) and one-sentence reasoning per dimension. Pass threshold: ≥ 0.70 (i.e., ≥ 4/5 raw score).

DimensionDefinition
faithfulnessEvery factual claim traceable to retrieved contexts (1=fabricates, 5=fully grounded)
completenessAll parts of the question fully addressed given available context (1=major gaps, 5=thorough)
citation_quality[N] markers placed immediately next to the specific facts they support (1=none/misplaced, 5=all correct)
hallucination_freeNo external knowledge beyond retrieved contexts introduced (1=adds external data, 5=purely corpus-grounded)

Judge Prompt (exact)

Score each dimension 1–5 (integer only): 1. faithfulness — every claim traceable to retrieved contexts 2. completeness — all question parts addressed 3. citation_quality — [N] markers placed next to facts they support 4. hallucination_free — no external knowledge beyond retrieved contexts Return ONLY valid JSON, no other text: { "faithfulness": {"score": <1-5>, "reasoning": "<one sentence>"}, "completeness": {"score": <1-5>, "reasoning": "<one sentence>"}, "citation_quality": {"score": <1-5>, "reasoning": "<one sentence>"}, "hallucination_free":{"score": <1-5>, "reasoning": "<one sentence>"} }

Heuristic Fallback

When Ollama is unavailable or returns malformed JSON, a word-overlap heuristic replaces the LLM judge. Faithfulness and hallucination_free use answer/context token overlap; completeness uses question keyword presence in answer; citation_quality counts [N] markers. All bin into scores 1–5 using fixed overlap thresholds.

A/B Test Orchestration

The A/B test runner evaluates all seven configurations sequentially, then produces a ranked comparison matrix. When --judge is enabled, the winner is determined by a composite score: ragas_score + judge_overall × 2 (judge weighted 2× for interpretability).

C:\Users\murta\anaconda3\python.exe scripts/run_ab_test.py --n 20 --judge # Evaluates all 7 configs × 20 QA pairs = 140 RAGAS + 140 judge calls

Development Methodology

The agentic development workflow followed a structured pattern:

  1. Natural-language specification: Each feature was described in plain language (e.g., "Add LLM-as-Judge with 4 dimensions, heuristic fallback, and API endpoint")
  2. Plan mode: Claude Code's Plan tool produced a file-by-file implementation plan for review before any code was written
  3. Autonomous execution: With plan approved, Claude Code implemented all files, ran syntax checks via hooks, and committed each logical unit
  4. Live debugging: When errors occurred (HNSW corruption, Windows OOM, RAGAS API changes), Claude Code diagnosed via log analysis and applied targeted fixes without human debugging
  5. Verification: Monitor tools watched background processes and reported results back to the conversation, enabling autonomous decision-making
